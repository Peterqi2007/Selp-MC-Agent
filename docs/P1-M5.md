### 5.9 M5-CU 前置门实现（离线，2026-10-18）

按要求"先修真机接线、不换采集路径、不跑真机 act"：本轮只交付**离线门**与**只读几何来源**，
没有执行任何真机 act，也没有改采集后端。

| 模块 | 职责 | 关键拒绝码 |
| --- | --- | --- |
| `windowPolicy.check()` | act 门 | `cu-unproven` `outside-window` `outside-bounds` `bounds-required` `coordinates-required` |
| `windowPolicy.checkObserve()` | 只读观测门 | `observe-window-required` `not-candidate-window` `candidate-not-unique` `interaction-not-allowed` `kind-not-allowed` |
| `windowPolicy.verify()` | F1 证据门 | `screenshot-required` `bounds-source-invalid` `window-mismatch` `bounds-invalid` |
| `guard.act()` / `observe()` | 策略 → 执行器唯一路径 | 拒绝时 `executed:false` 且执行器不被调用 |
| `preflight.act()` / `observe()` / `resolveRect()` | 宿主适配层入口 | 透传；`resolveRect` 先校验窗口再取几何 |
| `windowRect.resolveRect()` | 几何来源链 | helper → win32/dwm → `rect-unavailable` |

设计要点：

1. **读与做分两门。** `verify()` 之前 act 全部 `cu-unproven`；只读观测走 `checkObserve()`，
   只放行唯一候选窗口。截图**作为 act** 仍被拒，**作为观测**才放行——不让一个入口模糊两种风险。
2. **观测必须带显式 `windowId`**，且不得携带 `x`/`y`/`key`/`button`/`text` 等字段
   （`interaction-not-allowed`）。
3. **`verify()` 不再接受占位证据。** 旧用例里 `evidence: 'F1 pending'` 这种写法现在会被拒；
   仓库内两处旧调用已改为真实证据对象，仍保持原测试意图。
4. **rect 不能来自像素。** `screenshot-size` 不是合法来源，`normalizeRect()` 与 `verify()`
   双重拒绝；全来源失败返回 `rect-unavailable` 且**不带 rect 字段**，调用方只能写"bounds 待补"。
5. **Win32 探针只读**：只调 `GetWindowRect` / `DwmGetWindowAttribute` / `IsIconic`；
   契约测试断言脚本内不出现 `PrintWindow|BitBlt|SendInput|keybd_event|mouse_event|CopyFromScreen`。
6. **几何查询也受窗口门约束**：`resolveRect()` 先过 `checkObserve()`，非候选窗口的 rect
   根本不会被查询（测试用 spy provider 断言未被调用）。

测试：`p1:contract:test` 新增第 42 组 20 条（观测门、verify 证据门、rect 来源链、只读探针、
非候选窗口不查几何），当前总计 **206/206**；`plan:audit --stage p1` **105/105**；
`p1:verify` **11/11** 套件（含 P0 回归；`--fast` 10/10）。

**诚实边界**：这些模块目前**没有被打包的 DSH 插件调用**。`resources/app.asar` 不可改，
所以真机 `computer_use_*` 仍只受 helper 自身授权约束；F1 判定不变（未通过）。
本轮交付的是"**门可用且可测**"，不是"门已生效"。接线点就是 `CuPreflight`：
宿主适配层把 `computer_use_act` / `computer_use_state` 改走它，才谈得上真机限窗。

## 6. 只读 F1 观察例外（明文，**仅 CU 可选路径**）

为能测量 F1，保留一个**有限、可审计**的只读例外。它不等于 `verify()`，也不授予任何 act：

1. **仅唯一候选 Minecraft 窗口**：候选集合必须恰好一个窗口，否则 `candidate-not-unique` 拒绝。
2. **显式 `windowId`**：观测请求必须指名窗口，缺省即拒（`observe-window-required`）；
   非候选窗口即拒（`not-candidate-window`）。
3. **无 act**：请求携带 `x`/`y`/`button`/`key`/`text` 任一字段即拒（`interaction-not-allowed`）。
4. **截图只用于两件事**：确定 bounds 的佐证、验证限窗是否成立。截图尺寸**不得**反推 x/y。
5. **不等于 verify**：观测成功不改变 `policy.verified`；`verify()` 仍需成功截图 + 真实几何来源的 bounds。

该例外默认开启，可用 `new WindowPolicy({ readOnlyObservation: false })` 关闭
（关闭后观测返回 `observation-disabled`）。

## 7. 口径变更：M5 改走进程内输入层（2026-10-29 定）

### 7.1 为什么换

原方案（Q5/§1.8.3）是「复用 `dsh-computer-use` + 提示词限窗 + F1 证明」。实测与代码审计证明这条路在 P1 内**不可收敛**：

| 阻断点 | 事实 | 我们能改吗 |
| --- | --- | --- |
| WGC 取不到帧 | 全屏 429×270 / 窗口化 696×417，两次均 `截图未产出` + `Declared image type does not match its bytes` | 否（helper 侧，且日志不可得） |
| 策略接不进真机 | `WindowPolicy`/`ComputerUseGuard` 在 `src/` 内只被自己引用；`resources/app.asar` 只读 | 否 |
| 真机只读口径分裂 | 已授权应用为空时 `computer_use_state` 仍被放行（§5.5） | 否 |

三项都不属于本项目可控范围，继续投入只会重复得到同一个失败。

### 7.2 新方案：进程内输入层（in-process input layer）

Minecraft mod 在**游戏进程内**合成输入并抓图，经既有 HTTP 通道交给 Node；Node 仍是唯一身体执行权、
键鼠台账与结果验证的持有者。

| 能力 | 实现（mod 侧） | 相比 CU |
| --- | --- | --- |
| 按键（含长按） | `KeyMapping.setDown(true/false)` + 每 tick 维持，暴露 `body_key` / `body_hold(ms)` | 不需要窗口焦点，不需要 `SendInput` |
| 视角 | 直接写 `player.setYRot/setXRot`（限速率），暴露 `body_look` | 不需要像素坐标换算 |
| GUI 点击 | 容器槽位 API（复用现有 `click <slot>`），每次重读 `menu` 再点 | 不依赖 bounds/分辨率/缩放 |
| 视觉观察 | 帧缓冲 `Screenshot`/`glReadPixels` → JPEG → HTTP（事件驱动 + 按需） | 绕开 WGC 与 OpenGL 合成问题 |
| 状态观察 | 既有 `/state` 结构化字段 + `menu` 槽位快照 | 天然新鲜、可 diff |

**它不是能力降级**：原方案的限窗约束靠「外部插件 + 提示词」保证，新方案的约束是**结构性的**——
输入层只调用游戏内 API，物理上不可能触达游戏外的任何窗口或进程。代价是它**永远做不了游戏外的事**
（启动器/登录/其他程序），而 M5 的命题本来就把窗外操作定义为无意义。

### 7.3 闸门替换：F1 → F1'

| 闸门 | 断言 | 证据方式 |
| --- | --- | --- |
| **F1'a 结构性不可出界** | 输入/截图只走游戏内 API 与本进程帧缓冲；仓库内不出现 `SendInput` / `keybd_event` / `mouse_event` / `BitBlt` / `PrintWindow` | 契约测试对 mod 与 Node 源码做字符串断言（与 §5.9 第 5 条同款写法）+ 代码评审 |
| **F1'b 键鼠台账** | 任意时刻按下集合可枚举；游戏内暂停（PauseScreen）、死亡、断连、急停、取消、任务结束、进程退出时**全部强制释放**；单次长按有上限 | `InputLedger` 契约测试 + 真机故障注入（暂停/死亡/取消/断连各 1 次，结束后断言台账为空） |

F1' 不通过则**实现不得合并**；这里没有"标 N/A 放弃"的出口——因为不再依赖任何外部工具。

### 7.5 实现清单（后续按此执行）

3. **观察**：帧缓冲截图（事件驱动：提案接受、卡住/失败、结构遇到、按需工具）+ `menu` 槽位快照 + 既有 `/state`。

## 9. 通道选择：能力优先（L1 入口补全 + L2 决策，2026-10-29）

> **问题（已确认存在，不是错觉）**：在本节之前，架构里**没有**"什么时候用代码生成、什么时候用键鼠"
> 的判定机制。动作脑的提示词里命令清单是**硬编码 8 条**（goto/mine/chop/fish/withdraw/follow/stop/status），
> `key`/`hold`/`shot` 与 `code-skill` 从未出现在它能读到的任何地方；代码生成只有运维 HTTP 入口
> （`POST /code-skills/generate`，必须人写 prompt）。因此真实使用中"没有反应"是符合当时实现的。

### 9.1 L1 入口补全（可发现性）

### 9.4 生效条件

- **DSH 需要重载插件**才能看到新工具 `mc_capabilities`（`npm run dsh:install` 或重启 DSH 会话）；
  未重载时 Node 侧 `/capabilities` 与 `!capabilities` 已可用，但动作脑仍看不到该工具。
- **工具面是"每会话"的**：插件更新后，**已存在的会话不会刷新自己的工具清单**。2026-10-29 实测：
  同一 DSH 进程里新会话能调用 `mc_capabilities`，而插件更新前创建的会话仍只有旧的 11 个工具
  （它如实报告"我没有这个工具"）。**插件变更后必须新建会话**，旧会话无法就地升级。
- 动作脑会话 id 固定在 `config/agent.json` 的 `chat.harnessAgentId`；换新会话后必须同步，
  否则 Node 桥接会继续绑旧 id（旧会话仍是旧工具面）。
- 生成仍是**人工发起**：本策略只把"没有通道覆盖"这个事实显式化并指向生成入口，不自动写代码、不自动晋升。

## 10. 面朝方向感知：瞄准对象与朝向失效（2026-10-29）

> 之前"朝向"只有 `yaw/pitch` 两个角度，`target` 只报方块；对着生物时返回 `null`。三处补齐：

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| `target` 支持实体 | `ClientStateSnapshot.targetJson(LocalPlayer)`（`/state` 与 `target` 命令共用一个实现） | 优先用游戏自己的 `hitResult`（1.20 的拾取是实体感知的），回退 `player.pick(4.5)`；实体返回 `{type:"entity", name, entityType, id, kind, position, distance, health}`，方块返回 `{type:"block", name, position, face, distance}` |
| 计划后置条件 `targetIs` | `src/planner/verifier.js` | 支持 `{name?, position?, type?}`，位置容差 0.5 格；之前 `lookat` **没有任何后置校验**，现在"视线对准某物"可写成 postcondition；`hasConditions()` 同步计入（否则部分完成结算会把它当空条件） |
| 朝向变化使 `target` 失效 | `src/world/observation.js` | 缓存 `target` 时记录当时的 `{yaw,pitch}`；再次读取时若相机转过 **>2°**，即使 TTL 未到也判 stale 并触发刷新（`staleBecause:'facing-changed'`）；刷新失败时旧值标 stale 而不是冒充当前。新增 `_currentSnapshot()` 用 body 最新快照（后台 500ms 轮询）比对角度 |

离线契约（`p1:m5:test` **31/31**，已并入 `p1:verify` 12/12 套件）：
- `targetIs` 命中/名字不符/位置不符/无 target/非法 spec 五种路径；
- `hasConditions({targetIs})` 为真；
- 相机不动不刷新、转 40° 强制刷新并拿到新值、刷新失败时 `stale=true & staleBecause='facing-changed'`；
- 源码契约：`targetJson(LocalPlayer)` 共用、`EntityHitResult`/`entityType`/`health` 存在、插件全量观测字段含 `yaw/pitch/target`。

**真机证据（2026-10-29，真实服务器，`node scripts/m5-target-live-probe.js` 8/8）**：

| 断言 | 实测 |
| --- | --- |
| 瞄准地面 → 方块 target | `{"type":"block","name":"minecraft:grass","position":{24,63,81},"face":"up","distance":0.81}` |
| `target` 命令与 `/state.target` 一致 | 同一份 `{name,position,face,distance}` |

## 11. 截图触发策略与投递（2026-10-29）

### 11.1 什么时候截

| 触发 | 事件 | 说明 |
| --- | --- | --- |
| 失败/卡住 | `plan:partial`、`plan:failed`、`task:failed`、`task:quarantined`、`plan:step` failed/partial | 失败类**可越级顶掉**同任务的低优先级帧（实测 `plan:started` 与 `task:failed` 只差 5–100 ms，否则失败帧永远被"执行前"帧吃掉）；失败帧**不做感知哈希去重**；失败帧**等待在途的普通帧**（`_inflight`）而不是被丢弃 |
| 执行前状态 | `plan:started`、`proposal:accepted` | 一次任务一张，可被同任务的失败帧替换 |
| 地形新意 | 新维度、首次见到的模组方块 | 模组方块按 block id 去重，每 session 每 id 一次 |
| 兜底 | 每 **90 s** 最多一张 | **仅当动作脑有活跃任务**（planService.busy / hub.busy / brain 队列非空） |
| 未接线 | 新群系、新结构 | 快照没有 `biome`/`structure` 字段 → 明确不做，等 mod 侧补字段 |

### 11.2 成本控制

`config/agent.json` 的 `screenshot` 块：`maxPerTask:3`、`minIntervalMs:15000`、`maxEdge:768`（≈380 KB/张）、`keepFiles:20`（目录只留最近 K 张，超出按 mtime 删）、`dedupeDistance:5`（dHash 64 bit 汉明距离）、`repeatedFailureCount:3`（同因失败第 3 次升级为 `repeated-failure`）。

dHash 由 Node 侧解码 PNG 计算（`readPngLuma` 支持 8-bit 非交错 RGB/RGBA，zlib + 5 种 filter），不依赖 mod 变更。

### 11.3 投递：只以 steer 进**活跃 goal**，没有 goal 就丢弃

第一版用 `harnessBridge.forward()` → 插件 `/message` → `agent.followup()`，那只是**一条 user 消息**：没有 goal service、没有 goal rounds，动作脑不会因为它持续工作（2026-10-29 操作员指出："这个 goal 是 dsh 模式，不是你在文本里发一句就 ok"）。现改为：

1. `boundAgentId()` + `goalOf(agentId)` 查动作脑当前 goal；
2. **只有 `phase === 'active'` 才发**，消息里带 `goal id` 与轮次；
3. 没有 goal / goal 已 complete / 旧 bridge 没有 goal 查询 → **只记录 `steer dropped (...)`，不发文本**（帧、旁注、`/observe` aux 照常保留）；
4. 策略**不创建 goal**（操作员决定：只有在别处已建 goal 时才插话；建 goal 的成本与权限不交给截图策略）。

已知的 goal 注入路径（不依赖操作员）：**自主提案** —— 请求提案前注入 prep goal，玩家接受后注入 execution goal（`purpose:'execute'`，`maxGoalRounds` 由提案配置决定）。`!goal <文本>` **不是** DSH goal，只是 Node 本地任务路由器；`mc_plan`/`mc_step` 是回合工具调用，也不建 goal。

文本固定包含：

```
[截图/<reason>] <相对路径> (WxH, ISO时间)
当前 goal: <id>（phase=active，轮次 n/m）
事件: <eventType> · task=<taskKey>
结构化状态优先：仅当 mc_state/mc_observe 的结构化字段不足以判断时，才读取这张图；
成功/失败判定仍以结构化条件为准，图片只作辅助证据，不能把失败升级为成功。
```

### 11.4 结构化证据与辅助证据

- 每次截图在 PNG 旁写同名 `.json`（reason/taskKey/eventType/hash/尺寸/时间），复盘不必猜；
- `/observe` 响应新增 `aux.screenshot{path, reason, at, width, height, sidecar, hint}`；插件 `mc_state` 描述已声明"仅在结构化字段不足时读取，图不能升级成功"；
- 面板/测试入口：`GET /screenshots`（策略状态）、`POST /screenshots/capture`（显式补拍，仍受预算）、`GET /events/recent`（最近任务事件）。

### 11.5 证据

- 离线：`p1:shot:test` **17/17**（触发映射、最小间隔、每任务上限、去重与删除、keep-K、维度/模组方块新颖性、失败顶替 pre-task、失败等待在途帧、无 goal 不投递、旧 bridge 不猜测、源码/配置契约）。
- 真机：`12:07:54` craft 立即失败 → `task-failed` 帧落盘（`shot-2026-10-29T12-07-54-874Z.png` + 旁注），日志 `screenshot steer dropped (task-failed): goal-complete`（当时动作脑 goal 已 complete，按规则不投递）；同一时段 `mod-block-first-seen` 正常触发；`/observe` 的 `aux.screenshot` 返回路径与 hint。
- 同场景更早一次（12:06:32）观察到 pre-task 帧被**去重**掉（静止画面与上一帧 dHash 相近），失败帧因"失败不去重"保留——符合设计。

## 12. 玩家任务 → 动作脑 goal（2026-10-29）

### 12.1 问题

玩家下达的任务（`!chop`、`!mine`、面板命令、语言脑派发）全部汇到 `chat/commands.js` 的
`enqueue()` → `brain.enqueue`，只是 **Node 本地任务**：没有 harness goal、没有 goal round
driver、没有可被 steer 的会话。动作脑（DSH）从头到尾不知道玩家要它做什么——截图 steer 也就
没有落点。

### 12.2 现在的链路

```
玩家命令 → chat.handle(line)                  ← 记录 dispatchLine/dispatchSource
        → enqueue(task)
        → brain.enqueue 接受（accepted!==false）
        → ctx.taskGoals.maybeCreate({command,taskName,source})   ← fire-and-forget
        → bridge.boundAgentId() + goalOf() 查活跃 goal
        → 无活跃 goal → bridge.createGoal({purpose:'execute', maxGoalRounds:3})
```

- 覆盖：游戏内 `!xxx`、面板 `POST /command`、语言脑经 `chat.handle(..., {source:'llm'})` 派发的任务；
- **不重复执行**：goal 文本明确 "Node 侧已交给确定性技能执行（taskName），不要重复它的动作"，
  动作脑的职责是**监督 + 纠偏 + 如实报告**（`mc_state/mc_observe` 看真实结果，需要时 `mc_step`）；
- **只允许一个**：已有 `phase:'active'` 的 goal 时跳过（`goal-active`），不叠 goal；
- **去重**：同一命令 10 秒内不重复建 goal；
- **预算**：`maxGoalRounds` 默认 3（`config/agent.json` → `taskGoal`）；
- 失败只记日志，任务照跑（goal 注入不阻塞 ack、不影响任务结果）。

### 12.3 真机证据（2026-10-29）

`POST /command {"command":"!mine dirt 2"}`：

| 观测 | 结果 |
| --- | --- |
| `GET /task-goals` | `created:1`，`goal-5076ace5-61dd-4b37-ae24-eb9ca32d2d0a`，command `mine dirt 2`，task `mine` |
| 插件 `GET /goal` | 同一 goal：`phase:active`，`rounds 1/3` |
| 任务结果 | `task:done`（12:13:22，collected 2/2 dirt…） |
| goal 终态 | `phase:complete`，`rounds 1/3`（动作脑看到任务已完成，一轮内收尾） |

### 12.4 与截图 steer 的关系

截图策略只在 **`phase:'active'` 的 goal** 存在时插话（§11.3）。玩家任务现在会创建这种 goal，所以
任务执行期间发生的失败截图（`task:failed`）正好落在活跃 goal 里，steer 才有意义；任务结束后
goal 变 complete，后续截图按规则只落盘不插话。

**正向 steer 真机复现（2026-10-29 12:17，活跃 goal 存在）**：

| 时间 | 事件 | 观测 |
| --- | --- | --- |
| 12:17:01 | 玩家任务 `!mine dirt 8` | `taskgoal` 注入 `goal-7d16dd41-b52d-4724-a8d8-177b46de7925` |
| 12:17:05 | 失败计划的 `pre-task` 帧 | `screenshot steer delivered -> goal goal-7d16dd41… (pre-task)` |
| 12:17:35 | 计划失败（`body-busy`，被任务占用 30 s）`plan:failed` 帧 | `screenshot steer delivered -> goal goal-7d16dd41… (plan-failed)` |
| 任务结束 | — | goal `phase:complete`，`rounds 1/3` |

即：**活跃 goal 存在时，失败截图会以 steer 消息真正进入动作脑会话**；goal 结束后恢复"只落盘不插话"。

### 11.6 steer 直接携带截图（2026-10-29 修订）

只给路径时，动作脑要"先结束当前轮 → 下一轮再读文件"才能看到图（操作员指出："只 steer 不 send，agent 得等一轮"）。
现在 `/message` 接受 `imagePath`：插件用 DSH attachments（`ctx.get('attachments').saveImages`）把 PNG 转成
`{type:'image', attachment:{attachmentId,...}}` 内容块，与文本 steer **同一条消息**投递，收到的那一轮即可看到画面。

- 失败兜底：附件保存/读取失败时**不丢 steer**，文本末尾追加"截图附件发送失败：…；请按上面路径自行读取"，并记 warn；
- 返回体带 `image:{attachmentId,bytes,width,height}` 便于调用方确认；
- 桥接：`harnessBridge.forward(text,{imagePath})` → `POST /message {text,imagePath}`；截图策略用 `record.path` 传入；
- 生效条件：插件代码在 DSH 进程内（:8770 由 DeepSeek Harness.exe 提供），**必须重启 DSH** 才加载新版本。
