# 独立选型实验：coding harness 与自研动作脑对照及成本审计

> 日期：2026-10-16。状态：**实验设计与成本估算，尚未实现测试入口、尚未运行实验、尚无实测胜者。**本文不是执行报告，也不表示已安装/切换 harness、调用付费模型或修改游戏存档。
>
> **"成本审计"的口径（2026-10-16 修正）**：这里审的是**做这项测试本身要花的时间、token，以及产出的模块能否被 P1 复用**，目的是判断**这个实验有没有必要开展**。本文**不做经济性评估**：不折算人力费率、不设现金上限、不算回本周期（原因见 §8.4）。是否铺开完整批次由 §10 的决策闸门裁定。
>
> **触发方式（2026-10-17 定）**：P1 已决定**先接入 coding harness**，本文因此**默认不执行**。仅当 [`P1-PLANNER-PLAN.md`](P1-PLANNER-PLAN.md) §1.9.2 的两条降级判定（接口不稳定 / 预算边界不满足）任一成立时才触发，且**先做 §10 第 2 项（8 次配对运行）**；24 次完整批次仍受 §10 闸门约束。
>
> 与 [`P1-PLANNER-PLAN.md`](P1-PLANNER-PLAN.md) §1.9 相互引用，但**不属于 M0–M7 的新增阶段**。实验在独立夹具中比较两条路线，不要求先重构生产规划器、人格、聊天或记忆系统。结果用于选择下一步投入方向，不代替 P1 正式验收。

## 1. 要回答的问题与停止扩张的边界

本实验只回答：**在当前项目的模型、工具和异步任务条件下，采用 coding harness，是否比复用现有代码编写一个轻量动作脑更值得继续投入？**同时观察功能、集成工作量、运行时间/token 开销和一次接口变更的维护成本。

**本实验是条件动作，不是默认路线**：P1 先接 harness；只有 §1.9.2 的降级判定成立时才回到这里。

假设先登记，结果允许否定：

- H1：已有技能组合上，两者均可完成；自研适配成本可能较低。
- H2：遇到失败、缺知识和生成/修复代码时，harness 的通用设施可能减少自行开发工作，但不保证 token 或时延更低。
- H3：事件续轮、取消、模型兼容或用量不可观测，可能抵消 harness 的复用收益。

**范围固定为 24 次计分运行**：20 次真实模型＋Mock/夹具，4 次真实 Forge 客户端冒烟。每条路线各 12 次。加有限接口探针和开发调试，不扩大成两套生产系统。

不在此次实验中实现：语言脑/persona、普通聊天插话、完整长期记忆、复杂 GUI/computer_use、开放世界探索、矿洞全路径规划、在线技能正式晋升、多服务器管理。联网学习用冻结资料包替代，另测缺信息时求助；因此本实验不证明真实搜索可用性或时效性。

## 2. 两条路线的最小实现

| 项目 | A：coding harness | B：自研动作脑 |
| --- | --- | --- |
| 实现 | 首批优先使用固定版本 DSH；实际版本在开跑前登记 | 基于现有 LlmClient 和工具注册思想，写单一多轮工具循环 |
| 复用 | harness 的回合、工具、上下文和编码工作流 | 仓库已有请求、取消、Schema、工具调用和日志能力 |
| 必须补的薄层 | 工具桥、启动/事件续轮/取消、会话与 runId 关联、usage 汇总 | 工具派发、事件继续、有限重试/预算、会话状态和编码工具调用 |
| 等价能力 | 观察、技能执行、结果、提问、资料检索、文件读写、测试反馈 | 相同效果的工具；不能只允许一次 JSON 规划而不给反馈机会 |
| 不承担 | 改造生产 Node 运行时、开发完整 P1、替代既有 body/技能 | 多 agent、复杂搜索树、完整通用 coding harness 产品 |

Codex 是备用候选，本批次不同时测试 DSH、Codex 和 B 三套。DSH 不通过探针时先记录原因；决定试 Codex 则建立新批次和预算，不能把两种 harness 的成功样本拼成 A。接口调查依据见 [`HARNESS-INTERFACES.md`](HARNESS-INTERFACES.md)，适用范围以 P1 §1.9.2 为准。

### 2.1 独立测试宿主

建立只服务本实验的小宿主，复用 [`MockBody`](../src/body/mockBody.js)、能力/Schema 和现有技能中可用的部分。增加可控事件、初态重置、独立结果验证与账本。**最小身份关联、单执行者和停止是测试夹具需求，不要求先完成 P1 全量任务库和调度重构。**

建议结构如下，均为待创建位置，不是现有入口：

```text
experiments/planner-ab/
  manifest.json          # 冻结版本、模型、场景、预算和顺序
  fixtures/              # 初态、知识包、事件脚本；评分器不向 agent 开放
  adapters/harness/      # A 的薄接入层
  adapters/custom/       # B 的薄循环
  host/                  # 共用事件、验证、记账与重置
  workspace-template/    # 每次运行复制的空候选工作区
  results/<batchId>/     # 请求、事件、代码版本、成本与结果
```

不改生产默认配置，不覆盖日常 DSH/Codex profile，不自动注册生成技能。工程实现另起 `codex/` 分支；只增加实验入口和必要的可复用小适配，若必须先大改生产模块则停止并重估范围。

### 2.2 共用工具契约

工具名称为建议，允许不同传输方式，但两方可获得的信息、执行效果和反馈必须相同：

| 工具/事件 | 作用与约束 |
| --- | --- |
| `observe(fields)` / `capabilities()` | 返回有版本、时间和范围的状态与能力；不包含未来事件或评分答案 |
| `execute_step(skill, args, runId, stepId, attemptId)` | 单身体执行者；异步受理返回 accepted/taskId；技能结果另发事件 |
| `task_result(taskId)` / `task_finished` | 查询或接收对应终态和证据；事件由宿主触发下一轮，不要求模型反复查询 |
| `ask_player(question)` / `player_answer` | 保留未完成目标和具体问题；脚本化回答与请求绑定 |
| `read_knowledge(query)` | 只检索冻结资料包，两方拿到同一版本内容；不是实测联网搜索 |
| `read_file` / `write_file` / `run_candidate_tests` | 在隔离候选目录内生成、编辑、执行规定测试；不得改评分器、初态、主项目或账本 |
| `stop` / `cancelled` | 测试宿主直接停止执行、撤销旧输出资格，再通知后端取消；不依赖模型同意 |

A 可以保留等价的框架原生文件编辑方式，B 通过简单包装获得同等效果；不强求工具名称和提示词字节完全一致。两方均不能访问答案、额外世界数据或未记账的网络/子 agent。框架必需的工具说明和上下文开销照实统计，不能为了让 A 省 token 而隐藏其开销。

### 2.3 生成代码的试验边界

S5 只运行**面向模拟容器的短 JavaScript 候选程序**，不把实验代码加载到生产 Node，也不允许它控制真实玩家。生成和修复是真实模型完成，文件实际执行并检查状态变化，不能以“输出了代码”算通过。

执行条件：已有可用的 OS 隔离环境或容器，使用最小目录挂载、无网络、无凭据、限定资源和宿主强制超时；评分器在候选不可改写的位置。仅 `node:vm`、普通子进程、分目录或口头禁令不算安全隔离。A/B 的候选运行器相同。

首次探针检查这一前提。若本机缺少可用环境，本批次不临时建设完整生产沙箱：记录额外预计工作，S5 标未执行，整体结论降为“证据不足”。不能删掉代码场景后宣称已经比较完整 P1 的路线价值。上述局部隔离检查也不能代替 P1 A19 的完整边界验收。

## 3. 分步执行方法

### 3.1 先做低成本接口探针

1. 登记仓库提交、未提交变更摘要、harness/Node 版本、模型 ID/实际后端、端点标识、采样参数、工具集和有效配置摘要；配置脱敏，不记录密钥。资料包、夹具、提示词和代码记录 hash。
2. 确认 A/B 能使用同一模型快照/端点和相同可设置参数。只靠相同模型名称不足以证明相同后端；无法确定时明确记录。可控制的 reasoning/输出预算保持相同，不支持的字段如实标出。
3. A 验证：启动真实回合→调用只读工具→收到异步任务事件后继续→本地取消→丢弃迟到结果。确认无需人工点桌面继续、无需 LLM 定时轮询；测试候选目录与文件/测试工具可用。
4. B 验证相同生命周期；记录已有代码复用和新增工作，不能把全部旧开发成本算成 B 本次支出，也不能把新增修复算作免费。
5. 核实 usage 获取、预算控制和隔离运行器。若无法观察框架内部请求，则先记录是否可用供应商侧独立计量补足；**既看不到调用也无法限制用量时不进入计分阶段**。

**A 的宿主接入探针最多投入 2 人时**，计入 A 的开发预算；探针/开发的 token 预算见 §7。接口不通、必须大改宿主或只能靠未知内部补丁时，先停止并报告具体阻碍，不无限续写适配代码。可完成的工作与失败运行的用量仍记账。

同一模型不可实现时，可以继续比较“两套产品配置”的端到端效果，但表头必须列出不同模型，不能把差异归因于 harness 架构；纯架构比较结论标证据不足。

### 3.2 冻结后运行

1. 用专门调试夹具完成适配，不能用计分场景反复调提示词。冻结两方提示词、工具和预算；任务要求一致，框架必要说明允许不同且入账。
2. 每个场景预先确定两个初态/事件变体，二者都对 A/B 开放相同目标和初始信息。变体一顺序 A→B，变体二 B→A；真机 L1 用 A→B，L2 用 B→A。串行执行，避免共享资源干扰。
3. 每次重新创建工作区、重置世界/库存/设备、任务记录、候选代码和会话，不把上轮结果或方法写回下一轮。两方共享相同初态，模型若支持 seed 则固定，但不声称 seed 保证确定性。
4. 保存所有失败与超时。除预登记的场景异常外，基础设施故障记为 invalid 并保留其用量；本预算不安排自动补跑。样本不足就报告证据不足，补跑须另记批次，不能删除失败后补成功。
5. 模型内重试、工具修正和代码修复属于同一次运行，消耗同一预算；超额结束是正式结果，不重置 runId 洗掉失败。
6. 单独记录缓存命中、服务端排队、框架压缩/内部回合与工具等待时间。禁止为一方额外预热后隐去开销；必要预热进入该路线开发桶。

固定知识包与排除实验间记忆是为控制变量，不表示生产 P1 应放弃联网或长期学习。

## 4. 场景、数量和可检查的结果

### 4.1 真实模型＋Mock/可控夹具：20 次

每个场景 2 个预先冻结的变体 × 2 条路线，合计 `5 × 2 × 2 = 20`。每条路线 10 次，S4 是取消测试，其余 8 次是功能任务。

| ID | 目标与两种初态/事件 | 注入及判定 |
| --- | --- | --- |
| S1 现有技能组合 | 获取原木→加工木板→合成指定数量木棍；变体一无原料，变体二已有部分原料。数量、配方和工作台条件在夹具中固定 | 至少三个依赖步骤；用初末库存和消耗台账验证准确目标，已有材料应被利用。不得让夹具自动规划或代模型选技能 |
| S2 条件改变与异步恢复 | 获取目标材料→到设备加工。变体一首选设备在开始加工前失效但存在可查询替代；变体二首次获取仅部分入包 | 首个阶段已成功；某步骤延迟超过 11 秒；投递一次重复完成事件。应保留已完成步骤、按新条件继续；不得把受理或部分结果当全成功，不重复制造/消耗已完成产物 |
| S3 学习、求助、继续 | 生产夹具专用物品，资料包缺一个必要参数；变体一缺催化剂类型，变体二缺设备模式。缺失值不在初态或隐藏字段中泄漏 | 先查资料/能力，提出明确缺口问题；进入等待并在 60 秒无回答期不调模型。随后测试员按事先脚本给唯一正确指导，应关联并继续原目标。泛泛说“怎么办”、直接宣告干不了或自行猜值不算完成闭环 |
| S4 取消与迟到结果 | 变体一在模型请求在途时取消；变体二在异步移动已开始时取消，随后重放一条旧计划工具请求/完成事件 | 本地停止/撤权不等模型；取消确认后旧输出不产生身体动作，终态不改成功，无第二执行者。模拟时钟/Mock 只能证明逻辑；真实 3 秒停止要求另在 L2 测 |
| S5 生成并修复小技能 | 空模板生成 `fill_container(ctx, {source, target, item, targetCount})`，只提供读库存、部分转移、取消接口；两个变体分别含库存不足和中途取消/已有部分物资 | 第一段实际运行新代码，按可用物资填到目标并如实报 partial；第二段修复统一给定的缺陷候选（把请求量当实际转移量、取消后继续）。两段共享一个运行预算，须均通过独立验证 |

S1–S3 的设备、配方和知识反馈由可控夹具补齐，不宣称当前 Mock 已完整支持这些能力。现有 Mock 有平地/瞬时动作等简化，需设置动作延迟；不能用它证明实际寻路、拾取高度、GUI 或服务器行为。S4 在请求发出钩子/动作开始事件上触发取消；如果响应过快，可由测试传输层暂缓交付，记录这一注入，不将人工延迟算成模型时延。迟到请求重放是契约测试，不冒充模型自然产生的行为。

S5 的接口和测试规则明确给模型；可见测试返回错误事实，评分用独立固定测试检查库存不足、已达目标、部分转移、取消与重复执行。测试员不能替它写修复。第二段缺陷是统一人工注入，报告中与模型自行产生的 bug 分开，不能冒充“自然失败率”。生成文件、修复 diff、测试 stdout 和实际模拟库存变化均保存；自述通过无效。

### 4.2 Forge 客户端冒烟：4 次

先确认现有构建和确定性技能可执行该场景，使用可重置测试存档/区域与初态备份；沿用当前单服务器，不新建多服务器架构。真机计分前恢复同一初态、玩家位置、工具、库存、目标方块和环境条件。

| ID | 规模 | 操作与通过条件 |
| --- | --- | --- |
| L1 真实效果 | A/B 各 1 次 | 移动到指定工作区，挖掉一块外露目标矿并获得对应产物；产物初始为 0，无其他同类掉落物，工具合适。观察矿块与库存证据，由既有确定性采矿/拾取技能执行，不要求 LLM 逐格操作 |
| L2 真实取消 | A/B 各 1 次 | 启动固定短路线，收到动作开始事件后发本地停止；实测从收到停止到动作结束/按键释放 ≤3 秒。随后注入旧任务完成/工具请求，确认不恢复动作和不误报成功 |

L1 只能说明简单真实闭环，不能推广为斜向上拾取、复杂矿洞或整个挖矿计划验收。L2 只测一个真机取消场景，不能覆盖所有死亡/断线/GUI 情况。若客户端基线本身失败，保留原因并暂停该层，不把共同执行层的失败直接算成某个规划框架更差。

### 4.3 一次小型维护演练

计分冻结后，对 A/B 各做一次相同的公共契约 v1→v2 变更，例如工具参数 `skill` 改为 `capability`，终态证据增加必需版本字段。事先冻结变更说明和回放事件，测两侧适配/定位/回归的人时、修改文件和代码量。

用录制轨迹及确定性夹具回放，不新增计分模型运行，不另占模型额度。不得只在共用层吞掉变更后声称两边适配零成本；如果动态 Schema 的设计确实无需改代码，记录验证过程和 0 修改事实。此演练只提供一次接口变更样本，不能代表真实上游升级的全年维护成本。

## 5. 评分与选型规则

### 5.1 硬门槛与计分

按路线分别报告：

- **真实后置条件优先**：S1/S2/S3/S5 每条路线 8 次功能运行，建议门槛至少 7/8；S3 的两次均需有具体求助并恢复的证据，S5 两次均需完成生成和修复。这是有限样本筛选门槛，不是统计显著性结论。
- **控制门槛**：S4 两次取消均通过，L2 真机取消通过；计分阶段无取消后实际执行旧动作、无两个身体执行者、无绕过工具/目录边界。
- **效果门槛**：L1 真机入包通过；最终对外结果零虚报完成。模型曾误判而被验证器拦住的情况另计“被拦截误判”，不能隐藏为模型正确，但不等同于系统已虚报完成。
- **可归属门槛**：全部运行、模型请求和人工工作可归属；用量缺口有边界估计与原因，不能将缺失 usage 计为 0。不可控/不可观测的隐藏请求使用量比较不合格。

S4/L2 的预期结果是 cancelled，不能因没有产物判失败，也不能混入功能完成率分母。所有运行保留 `completed / cancelled_as_expected / failed / budget_exhausted / invalid / not_run` 与失败原因。夹具正确阻止的违规工具请求记录次数；真正越权执行属于硬门槛失败。

记录每次调用数、输入/缓存/输出/推理 token、工具次数、任务总耗时、模型/工具/等待耗时、重复动作、恢复次数、被拦截误判和代码修复次数。样本太少，主要展示逐次值、范围和中位数，不用 p95 或小幅百分比差声称稳定优势。

### 5.2 选择逻辑

1. 只有一方满足全部门槛：优先继续投入通过方，明确另一方失败源于适配、模型、规划还是共用执行器。
2. 两方均通过：比较路线专属开发＋维护人时、全量 token 与请求数、完成时延与功能覆盖；一方在功能不退步时**同时**降低人时和运行开销，优先该方。
3. 存在取舍：按 §8 的真实数据和预计后续任务量做敏感性分析（人时与 token 两个维度分别看）。差异不足一个配对任务、少于约 2 人时或容易被缓存/服务抖动解释时，不急于宣布胜者；这些是决策保守带，不是统计检验。
4. harness 功能合格但宿主集成复杂，自研规划更轻且 harness 编码明显有利：可提出“自研动作脑＋harness 编码后端”的下一阶段验证，不宣称本实验已验证两者组合。
5. 两方均失败、缺代码场景、缺真机层、同模型条件不成立或账本不足：明确写证据不足/仅产品配置比较，列下一项最小验证。不得删场景、加预算无限试到想要的结论。

不以总分掩盖停止/执行边界失败，不按生成计划文本的长度或“看起来聪明”评分。24 次运行不证明全部挖矿任务的泛化、自主生活可靠性或长期维护收益。

## 6. 时间成本与复用性审计（本实验值不值得做）

> 本节回答三个问题：**要做多久（人时）、能留下什么（可复用模块）、因此这笔投入是"净重付"还是"预付"。**
> 不做经济性审计：不折算人力费率、不做金额预算、不算回本点。判断依据只有时间、token 和模块复用三项。

### 6.1 人时口径与分桶

假设由熟悉仓库的开发者执行，既有客户端可运行、依赖不需大规模安装、隔离候选运行器可复用、A 有可用宿主入口。以下是**规划估算人时，不是承诺工期**：

| 工作项 | 归属 | 估算人时 | 交付依据 |
| --- | --- | ---: | --- |
| 共用夹具、初态、事件、验证器、账本 | shared | 5–7 | 可重置场景和独立结果/用量日志 |
| A 接入与接口探针 | A | 3–5 | 能启动/续轮/取消、工具和 usage 连通；含最多 2 人时的首轮宿主探针 |
| B 薄循环与编码工具包装 | B | 3–5 | 相同工具效果、有限多轮、恢复和取消 |
| 配对运行、真机重置与失败复核 | shared | 3–5 | 全部样本或未完成原因、真机证据 |
| A 接口变更演练 | A | 1–2 | 修改记录与确定性回放 |
| B 接口变更演练 | B | 1–2 | 修改记录与确定性回放 |
| 汇总、用量对账、选择记录 | shared | 2–3 | 审计与结论报告 |
| **总计** | **shared 10–15；A 4–7；B 4–7** | **18–29** | 不把 shared 重复加到总账 |

建议总人工硬上限 **32 人时**，达到约 26 人时（80%）评估剩余工作，超上限停止扩张并提交已得证据。A/B 专属总估算均为 4–7 人时，实际不强行做成相等。

**人时口径必须写清的两条**：

1. **只有人工监督等待才计人时**；纯机器等待（模型回合、任务事件、60 秒脚本回答窗口）计运行时间，**两者不得相加冒充人时**。
2. **开发者用 coding 助手写适配代码所消耗的 token 另入 §7 的探针/开发桶**——漏记这部分会让"时间成本"看起来比真实低。

缺隔离环境、宿主内部改造、客户端基线故障或供应商协议修复不在上述正常假设中；单独估新增工作，**不自动突破 32 人时**。必要时本次以不可行/证据不足结束。

### 6.2 模块复用审计：哪些产出是资产，哪些是沉没

判断"实验值不值得做"的关键不是总人时，而是**其中有多少能把 P1 的生产接入工作提前做掉**。

| 能力 | harness（A）自带 | 本仓库已有 | 本实验新增 | 复用去向 |
| --- | --- | --- | --- | --- |
| 模型多轮回合 | 自带（含压缩、工具后续回合） | `LlmClient` + 有限回合 | A 只需接线 | **A：实验后可直接演进为生产接口** |
| 工具注册与派发 | 自带（插件 / MCP） | 工具注册表 + Schema 校验 | A 写工具桥；B 写派发 | A 桥 ≈ P1「harness → Node」契约实现 |
| 上下文压缩与结果裁剪 | 自带（结果裁剪阈值、溢出落盘） | 无等价物 | 不新增（B 侧需自建简化版） | A 直接受益；B 若落地要补 |
| 取消 / 中断 | 自带生命周期 | 有取消、`holds` 停牌、generation 推号 | 两侧都要适配 | 适配层可复用到生产 |
| 事件续轮（异步任务完成后续跑） | 需探针确认 | TaskHub 已有异步受理与事件 | 两侧都要写 | **探针结论直接决定 P1 接法** |
| usage / 预算会计 | 自带（可观测程度待探针） | 有 token 账本与预算闸 | 对齐口径 | 账本格式可复用到生产审计 |
| 沙箱化候选代码执行 | 自带（受限执行） | 无（本仓库不加载生成代码） | 两侧共用运行器 | 生产「技能试运行」需要同一套 |
| 冻结夹具 / 初态 / 事件脚本 | 无 | `MockBody` + 可复用技能 | shared 新增 | **一次性**：主要为对照公平性服务 |
| 评分器 / 结果验证 | 无 | 验证思想（入包证据等） | shared 新增 | 部分可复用（验证方法） |
| 运行账本与对账 | 无 | 无 | shared 新增 | 格式可复用；本次数据一次性 |

**读法（核心判据）**：

- **A 路线的「工具桥 + 生命周期适配」是本实验最有复用价值的产出**——它就是 P1 §1.9 里"harness → Node"的那层契约。若 A 最终被选，这 4–7 人时是**预付**而不是重付。
- **shared 的夹具、初态、评分器、账本基本是一次性的**（10–15 人时）——它们只服务"公平对照"这一目的。**这是本实验最需要被质疑的部分**：如果结论已经能从更小的 spike 得出，这 10–15 人时就是纯支出。
- **B 的薄循环（3–5 人时）**在选定 B 之前不构成资产；但如果结论是"自研动作脑 + harness 编码后端"，它仍有价值。
- **复用率要写成数字**：`可复用产出的估算人时 ÷ 总人时`。低于约 1/3 时，实验主要成本是"为了对照而对照"，应先做 §10 的最小验证再决定是否铺开。

### 6.3 结论怎么用

- 若 §10 的第 1 项（接口 spike）不通过：**A 路线直接停**，无需再做对照——B 不需要 A 做陪练，可直接进入 P1 的自研设计。
- 若 spike 通过、且预计可复用产出 ≥ 总人时的 1/3：本实验按 24 次计分运行执行（预算见 §7）。
- 若 spike 通过但可复用产出明显低于 1/3：把规模压到 §10 第 2 项的 8 次配对运行，只回答"两者的规划质量与恢复能力是否可区分"。

## 7. token 预算与止损（只记用量，不折算现金）

> token 预算在这里只有一个作用：**给两方同一个停止条件**，让对照公平、让单次运行不会无限跑。
> 它是"跑飞保护"和"可比性装置"，不是费用清单——因此**不引入价格表、不折算金额、不设现金上限**。
> 本文的 token 上限**只是实验内的公平性装置**；生产按 P1 §1.9.6 **不做代码级 token 限制**，两者不要混用。

### 7.1 调用和 token 上限

为便于事前审核，首批使用相同硬预算；预算不足也是结果。所有用户回合、工具后续回合、模型重试、压缩/总结、框架内部及获准的辅助模型请求都占额度。首批禁用不必要的子 agent，不允许转到未记账账户继续。

| 桶 | 次数/规模 | 请求上限 | 累计输入上限（含缓存） | 累计计费输出上限（含去重后的推理） |
| --- | --- | ---: | ---: | ---: |
| 每次计分运行 | A/B 同标准；含修复/重试 | 12 | 100,000 | 20,000 |
| 每条路线计分合计 | 12 次运行 | 144 | 1,200,000 | 240,000 |
| 两路线计分总计 | 24 次运行 | 288 | 2,400,000 | 480,000 |
| 探针/预热/开发调试 | 每路线最多 12 请求、100,000 输入、20,000 输出 | 24 | 200,000 | 40,000 |
| **首批总上限** | **计分＋探针/开发** | **312** | **2,600,000** | **520,000** |

这些是预算上界，不是预测两方会用满。每条路线含开发共 **156 请求、130 万输入、26 万计费输出**。失败、网络重试、取消在途都计入已启动请求；确未发往供应商的本地校验失败另记，不伪造模型调用。开发阶段用录制/注入响应调接口，真实模型额度用完不另开未记账对话补调试。

每次运行总时限建议 **12 分钟**（包括 S3 的 60 秒脚本等待），工具调用最多 60 次、身体动作请求最多 20 次；单模型请求设置输出上限不超过 8,000，且不超过本次剩余额度。24 次串行计分的时间上界为 288 分钟；探针/开发真实请求另限合计 60 分钟。**这 348 分钟只是模型运行阶段的时限相加，不是开发总工期**（开发人时见 §6）。一次请求包含多个工具调用时，模型请求计 1，工具逐个计数，身体仍串行。

### 7.2 token 估计的依据与必须实测的两项

上面的数值是要被验证的假设，不是从实测外推的结果。**"每请求 10 万输入"偏乐观，已有数据点说明工具面本身就很贵**：

| 依据 | 数值 | 对本预算的含义 |
| --- | --- | --- |
| 同生态项目的工具描述总量断言（对方 README 自述；34 个 `mc_*` 工具的说明） | **≤ 18,000 字符**（约 5–6k token），**每次请求都随工具面重发** | A 路线工具面一大，**光工具说明就占单请求输入的约 5–6%**，且随回合数线性累积 |
| DSH 的溢出与裁剪阈值（本机随包文档） | 单条工具结果内联上限 **12,500 token**；结果裁剪保留 8,192/4,096/1,024 字符 | 一次大观察结果就能吃掉单请求预算的 12% |
| 本项目生产会话（本机 session 记录） | 仅 system 节点即约 **1,486 token**，工具 schema 逐项另计 | B 路线同样有工具面成本，不能假定 B 天然更省 |
| 生产 agent 单次任务的模型请求数（本项目运行日志） | 单次玩家请求常见 **2–4 个请求**，工具轮多时更多 | 每运行 12 请求的上限"够用但紧"，需 S5（生成＋修复）实测验证 |

**必须在探针阶段实测并回填的两项**（否则本预算只是纸面数字）：

1. **A 路线的固定开销**：首次请求的工具说明＋系统提示词占多少 token（决定"每请求 10 万"是否够 12 个请求）。
2. **B 路线的固定开销**：最小工具面＋循环胶水提示词的同等数值，用于确认两方**起点可比**。

若实测显示固定开销使 12 请求预算不足，**先统一上调两方预算**（保持相同）再开跑；不允许单方面给 A 放宽——那会让对照失去意义。

### 7.3 用量口径与去重（不涉及价格）

开始前保存**用量口径**：供应商如何定义 prompt/completion、缓存是否计入 prompt、reasoning 是否含在 completion 内。规范化为互不重叠的桶：

```text
Cu = 非缓存输入 token
Cc = 缓存命中输入 token
Co = 输出 token（按供应商定义，可能已包含 reasoning）
Cr = 仅在未包含于 Co 且单独计量时的 reasoning token
```

- 若 `prompt_tokens` 包含缓存，先减去缓存命中再算 Cu；若 `completion_tokens` 已含 reasoning，不能重复计一次 Cr。
- 不同供应商定义不能因字段同名而混算；**原始 usage 与规范化值一起保留**。
- **请求无 usage 时**：记为 unknown 并给出可证明的上界，**不记 0**。若无法为隐藏调用/推理建立有效上界，就不能声称实现了硬 token 上限——应停止计分并记录缺口。
- 缓存写入与命中若口径不同，拆成独立桶分别记录。

**这些桶只用于"谁用了多少、是否超限、是否可比"，不做任何金额折算。**

### 7.4 额度占用与在途预留（资源视角）

若使用订阅制额度或供应商配额，**额度占用本身就是成本**，必须记账：

| 要记的 | 说明 |
| --- | --- |
| 本次新增消耗 | 计分＋探针/开发实际消耗的请求数与 token |
| 额度占用 | 在订阅额度/速率限制里占掉的份额（与 token 口径不同时分别记） |
| 在途预留 | 已发出但未结算的请求，按本次剩余额度预留，避免"先超再发现" |
| 不可观测部分 | 框架内部调用无法观测时，单列 unknown 及上界，**不能记 0** |

发起每个请求前，**累计已结算用量＋在途最坏用量＋新请求最坏用量**必须落在该路线额度内；并发/自动重试同样先预留，能串行就串行。达到额度 80% 或剩余无法覆盖下一次请求时暂停新调度并记原因。

若宿主无法在内部请求边界拦截/限额，应使用可验证的供应商配额机制或实现预算适配；**只有轮后总 usage 而没有可控上界时，不能承诺严格封顶**，报告中应降级为"用量不可严格封顶"而不是假装有上限。取消不保证不消耗；迟到的 usage 到达后继续对账。

> 本节刻意不设"金额上限"。理由：本阶段目的只是判断实验是否必要、对照是否公平；经济性评估需要生产化成本与实测收益，当前都不存在（见 §8.4）。

3. 检查缓存和推理去重、重试/失败/取消的用量、开发/预热用量、订阅额度占用，验证总数不超各层限额；超额保留违规事实，不能删请求回到预算内。
4. 人工记录按 shared/A/B 分开，并按 §6.2 标出**哪些产出可复用、哪些是本批一次性**。报告"本次新增时间与 token 投入＋可复用占比"，已有客户端/技能/模型客户端是既有投入，不假设从零重写，也不把继承能力当成本次成果。
5. 功能失败归因至少分：模型规划、工具/端点兼容、宿主续轮/取消、共用技能/物理、夹具缺陷、预算耗尽。复核可以修复夹具用于新批次，本批旧失败记录仍保留。
6. 人工干预一旦改变计划、代码或任务结果，该次不能记为独立完成；按结果记录 assisted/失败说明，人工与模型用量照计。标准玩家指导、预定取消和初态重置不算额外救场。

### 8.3 比较公式（人时与 token 两条线，不折算金额）

```text
批次总人工   = Hshared + HA + HB                        （单位：人时）
A 专属投入   = HA 人时；另记 A 的请求数与 Cu/Cc/Co/Cr
B 专属投入   = HB 人时；另记 B 的请求数与 Cu/Cc/Co/Cr
可复用占比   = 可复用产出的人时 / 总人时          （§6.2 的判据）
```

两条线分开报告，**不得相加成一个"总分"**：人时回答"要投入多少时间"，token 回答"要占用多少额度、对照是否公平"。共用成本要么单列，要么按 §8.1 的规则各半分摊并注明，不能重复计一次。

每条路线功能任务为 S1/S2/S3/S5 的 8 次加 L1 的 1 次，共 9 次；取消测试另有 3 次。报告：

- 每次功能任务的**平均 token 与请求数** = 全部功能运行用量 / 已启动的功能运行数，失败也在分子中。
- 每个完成任务的**平均 token 与请求数** = 全部功能运行用量 / 通过独立验证的功能完成数；分母为 0 时写 N/A，不能写 0。
- 取消控制用量、探针/开发用量、维护演练人时**单列**；若报告"全部实验用量/成功数"，名称必须注明含控制与开发，不能与上一指标混用。
- 两方都完成的配对样本可作时延/用量比较，另附全样本失败及总用量，不能只展示共同成功样本掩盖失败开销。

### 8.4 为什么不算钱（明确不做经济性评估）

要把人时折算成钱、或算"多久回本"，至少需要三项**当前都不存在**的数据：生产化后的接入成本、每个同类任务实测节省的全成本、以及本项目认可的人力费率口径。本实验只能给出前两项的**实验内**近似，且样本量（24 次）不足以外推到生产。

因此：

- 本文不提供任何金额、汇率、价格表或"总上限折算"。**旧版本里的金额示例已作废**，看到请忽略。
- 需要经济决策时，另开一次**基于生产化数据**的评估；本文结论只作为它的输入之一。
- 本实验的真正产出是三项：**接口结论（A 能否接）＋ 复用清单（能留下什么）＋ 人时与 token 实测值**。
