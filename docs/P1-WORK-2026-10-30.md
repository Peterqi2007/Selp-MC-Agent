## 2. 感知层：骑乘状态 + 载具内部物品 + 载具完整度

### 2.1 数据形状（`/state`）

```jsonc
"mounted": true,
"riding": {
  "id": 77, "type": "entity.minecraft.chest_boat", "name": "minecraft:chest_boat", "kind": "vehicle",
  "position": {...}, "distance": 0.0,
  "passengers": [{"id": 1, "name": "AgentDeepSeek", "isPlayer": true}],
  "saddled": true, "chested": false,              // 仅当实体实现 Saddleable / AbstractChestedHorse
  "integrity": {
    "known": true, "current": 0.62, "max": 1.0, "unit": "ratio",
    "inferredMax": true, "source": "getHealth"    // or living/points, getDamage/points
  },
  "inventory": {
    "known": true, "source": "container", "size": 18, "occupied": 1,
    "items": [{"slot": 2, "item": "minecraft:coal", "count": 5}]
  }
}
```

### 2.2 覆盖范围（原版 + 模组）

| 载具 | 物品来源 | 完整度 |
| --- | --- | --- |
| 船/箱船、矿车箱/漏斗（原版） | `Container`（`ChestBoat`/`AbstractMinecartContainer` 都实现它） | 无（`known:false`） |
| 马/驴/骡/羊驼/骆驼 | Forge `IItemHandler`（Forge 补丁把马背包包成 `InvWrapper`） | `LivingEntity` health/maxHealth |
| Immersive Aircraft（`InventoryVehicleEntity implements Container`） | `Container` 槽位 | `getHealth()`，0..1 比例；无 `getMaxHealth` → `unit:"ratio"` + `inferredMax:true` |
| 其它模组载具 | 先 `Container`，再 `ForgeCapabilities.ITEM_HANDLER` | `LivingEntity`，否则反射 `getHealth/getMaxHealth`，再 `getDamage/getMaxDamage`；都没有 → `known:false` |

- 槽位枚举上限 `MAX_VEHICLE_SLOTS = 64`，只列**非空**物品（含 `slot`/`item`/`count`，可损坏物品附
  `damage`/`maxDamage`）。
- 反射只调**公开无参**访问器并吞掉异常：一个坏模组不能把 `/state` 打挂；读不到就诚实 `known:false`。

## 3. `@` 自然语言请求 → DSH goal

**问题**：`@` 通道（`chat.actionBrain=harness`）只把原文当**一条消息**转发给动作脑；没有 goal，
就没有 goal round driver，也没有截图 steer 的落点。`!` 任务有 goal，`@` 任务没有——同一个玩家意图
走了两套生命周期。

**修复**：
- `src/core/taskGoal.js` 新增 `maybeCreateDialogue({text, speaker, source})`：goal 正文保留原文
  （JSON 转义）、说明「原文已作为消息投递」，并要求动作脑**跨轮做完**；聊天类用 `mc_say` 回答后
  `update_goal complete`，动手类走能力优先 + 失败两次换输入层。
- `src/chat/dialogueRouter.js`：在**成功转发之后**调用（原文逐字投递的 A02 契约不变），
  `lastDialogueRoute.goal` 记录 goalId；失败/无 goal 服务只记日志，不影响请求。
- `src/index.js` 的 `ctx.forwardToActionBrain` 也做同样的事：**unified 语言脑与 addressed 通道直接走
  这个函数，不经过 DialogueRouter**；只在两处都接，`@` 才不会因为模式不同而漏 goal。
- 复用同一套护栏：单活跃 goal（`goal-active`）、同文本 10s 去重、`maxGoalRounds=3`。
- 测试：`p1:taskgoal:test` 12/12（新 3 条）、`p1:m6:test` 25/25（新 1 条）。

**注意**：聊天型 `@` 也会拿到一个 goal；goal 正文明确要求「纯聊天答完就 complete」，成本被
`maxGoalRounds` 限住。如果以后要区分「聊天/任务」，应在语言脑侧先分类，不要在 router 里做正则。

## 4. 截图 steer：从「等下一轮」改为「主动提交」

**问题**：插件 `/message` 用 `agent.followup()` → DSH 的 **next-turn** 收件箱；当前回合不结束就
看不到。失败截图恰恰只有当前回合有用。

**修复**：
- 插件 `/message` 增加 `mode`：`steer` 走 **`agent.steer()`**（DSH 的 next-step 收件箱，当前回合
  下一步就能看到）；`followup` 保持旧行为。运行时没有 `steer()` 时**诚实回退**并在响应里写
  `delivery:"followup"`，不假装已即时。
- `HarnessBridge.forward(text, {mode:'steer'})` 透传 `mode`，响应暴露 `delivery`。
- `ScreenshotPolicy` 的 steer 固定 `mode:'steer'`。
- 离线：新增 `p1:steer:test` 8/8（真插件 + 假 live agent，断言 steer/followup/回退/桥接/策略），
  `p1:shot:test` 20/20（断言 `meta.mode === 'steer'`）。
- **生效条件**：插件代码在 DSH 进程内，**必须重启 DSH**；本轮按口径跳过（见 §7）。

## 5. Voyager 式自动课程（automatic curriculum）

### 5.1 参考

- `refs/Voyager/voyager/agents/curriculum.py`：维护 `completed_tasks` / `failed_tasks`，
  把当前观察 + 已完成 + 太难的失败任务交给模型，要求「不要太难、要新颖、必要时才重复」。
- `refs/Voyager/voyager/prompts/curriculum.txt`：任务格式（单句）、mentor 语气、避免需要视觉确认的
  建筑/放置类任务。

### 5.2 实现（`src/planner/curriculum.js`）

| 能力 | 内容 |
| --- | --- |
| 难度表 | 按命令表 type + `args.block/item` + 数量分 1–5 级（`chop`1、`craft`2、`mine iron`2、`mine diamond`4、`shoot`3…） |
| 难度带 | `level = 1 + floor(completed / bandStep)`，默认每 2 个完成 +1，封顶 4 |
| 历史 | `completed`/`failed` 列表，原子写 `runtime/curriculum.json`（temp+rename），重启恢复 |
| 上下文 | `describe()` 输出 Voyager 形状的块：Completed / Failed / 当前 band / 上次完成 / focus / 5 条规则 |
| 校验 | `validate(candidate)`：低于 band → `difficulty-below-curriculum`（模型可重试）；连续 `maxRejections` 次后 `curriculum-relaxed` 放行，**不死锁** |
| 闭环 | 执行 goal `complete` → 记完成并升 band；`blocked` → 记失败（太难的先避开） |

### 5.3 接线

- `AutonomousProposalCoordinator.startPrep()` 把 `curriculum.describe()` 追加进 proposal-prep goal；
  插件 `proposalPrepObjective` 的 `CONTEXT: ${goal}` 原样带给动作脑（**不需要改插件**）。
- `Brain.proposeFromHarness()` 在 autonomous 分支先 `validate()`；拒绝时返回 required/actual/level
  与可读 detail，模型可改提案。
- `GET /curriculum` 与 `/ui/state.curriculum` 暴露 band/历史/最近校验（只读）。
- 配置：`planner.autonomousProposals.curriculum`（enabled/file/bandStep/maxLevel/maxRejections/historyLimit）。

### 5.4 测试

`p1:curriculum:test` **8/8**：难度表、band 增长与封顶、拒绝→重试→放宽、上下文内容、
持久化恢复、prep goal 携带上下文、执行 goal 结算写入、接线源码断言。

### 5.5 限制

- 难度表是启发式，不是模型判定；未知类型按 1 级。
- 真机/真实模型的「提案是否真的变难」**未验证**（需要 DSH 动作脑 + 游戏；本轮跳过）。
- 「automatic curriculum」是**提示 + 校验**，不是自动生成任务文本；任务仍由动作脑提出。
  如果模型持续无视 band，`maxRejections` 后会放行——这是有意的（宁可略简单，不可卡死）。
