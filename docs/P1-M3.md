## 2. 设计边界

### 2.1 恢复的是问题与计划，不是动作

- 在途任务、身体所有者、LLM 回合都不进入快照；重启后绝不重放。
- 恢复出来的提案是 `awaiting`，**不是同意**；玩家回答后才执行，过期问题在下次提案时被清理。
- 恢复的计划是 `waiting/completed/failed/pending`，**不会自动 start**；`restoreQuestions()` 只为
  停在 `waiting` 的步骤补一个问题，不改写步骤。
- 预算数值（3/2/2）是 P1 的初始建议，**不是实测结论**；A15 的阈值仍需真机记录后调整。
- 验证只读观察数据，不触发扫描；`ok:true` 不再是成功的唯一证据，后置条件说了算。
- 没有后置条件的计划无法自行证伪任务自报（live mock 已复现：P0 的零采集成功语义会使
  `mine dirt` 计划完成）；A13 的场景必须给可核对的终态。

### 2.2 持久化在测试窗口启用

- `config/agent.json` → `state.enabled=true`，路径 `runtime/p1-state.json`（gitignored）。
  这是为了 A17/A29 能在客户端窗口直接执行；此前“默认关闭，验收后再开”的约定由本次
  用户目标（M3 具备测试资格）暂时改写。
- 离线套件通过 `P1_STATE=off` 或显式 `options.state` 隔离，不读写 live 状态文件；
  `p0:verify`/`p1:verify` 的子进程也强制 `P1_STATE=off`。
- 若客户端窗口需要回到“不写盘”，把 `state.enabled` 改为 `false`（或启动时设
  `P1_STATE=off`）即可，不需要改代码。

### 2.3 续轮边界（F2）

- 已接线的是“计划/任务结算 → `turn:resumable` → SSE → 插件 followup → finish”。
- 等待玩家的计划在**重启后**恢复问题；如果模型回合已经结束，玩家回答后计划会继续执行，
  但不会自动唤醒已结束的 harness 回合（这是 A17/A14 的测试边界，不是静默重放）。
- 插件的新工具/续轮监听需要**重装并重启 DSH** 后才会加载；H1 仍可用 `/goal` 验证。
