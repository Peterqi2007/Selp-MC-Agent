## 2. 验证方法与判定规则

### 2.1 一条主张的格式

每个客户端项必须写成可证伪主张，而不是任务：

| 字段 | 要求 |
| --- | --- |
| **主张** | 一句话，能被一次观察否定（例：“任务返回 ok 时，库存必须增加”） |
| **仪器** | 命令/脚本/探针/事件流/面板；说明输入与观测点 |
| **正向证据** | 世界/背包/事件 ID/seq/token 的真实变化 |
| **反证（阴性控制）** | 什么观察会判定主张为假；仅“看起来正常”不算 |
| **有效性边界** | 这个测试**不能**证明什么（地形、模型、样本量、宿主） |
| **判定** | PASS / FAIL / INVALID / PARTIAL / BLOCKED / N/A |

### 2.2 证据等级（从强到弱）

1. **真实效果**：方块状态、背包数量、位置、实体、文件、窗口外拒绝。
2. **协议回读**：`/state`、事件 `seq/eventId`、`/events`、token 计数、审计账本。
3. **日志/截图**：只能作辅助，不能单独证明成功。
4. **任务自述**：`ok:true`、模型说“完成”——**永远不能单独作为通过证据**。

### 2.3 环境有效性门（先判“有效”，再判“通过/失败”）

每次执行前记录并确认：

- 存活、无界面、鼠标已捕获、维度正确；
- 背包/工具/目标存在（例如挖石必须有镐且点位有石）；
- 白天，或床可达并已入睡；
- 服务器响应正常、账号已登录；
- 客户端/模组/服务端/模型版本与配置。

**任一不满足 → 本次结果记为 INVALID，不记 FAIL，也不得写成通过。** 之前“挖石 32 noPath”
里就混有死亡界面/空背包/屋顶点位，属于 INVALID 或能力范围问题，不能一概算路径缺陷。

**M1 例外**：按 §2.5，M1 只验工作流。环境不满足但 agent 正确识别、明确报告、不虚报完成、
保持不变量时，这次观察可以作为 **M1 工作流正向证据**，而不是 INVALID；只有观测本身被破坏
（死亡界面/断连/无法读取）才记 INVALID 重跑。

### 2.4 阶段判定

| 判定 | 含义 |
| --- | --- |
| **PASS** | 阶段所有必需主张都有有效正向证据，且阴性控制未被触发；离线回归通过；无开放关键失败 |
| **PARTIAL** | 有部分主张通过，但仍有必需项未执行/INVALID；**阶段不通过** |
| **FAIL** | 必需主张被有效证据证伪；阶段不通过，先修复再重测 |
| **BLOCKED** | 外部前置缺失（模型/玩家/CU/harness/代码执行授权）；不是通过 |
| **N/A** | 只有文档明确允许时（例如 F1 失败后 A21/A22），且必须记录理由 |

**阶段闸门规则：离线套件全绿只是入场券，不能替代客户端证据。**

### 2.5 M1 专项口径：工作流正确性 ≠ 任务完成

M1 的测试对象是**身份/事件/能力/进度/执行权/停止**这条工作流，不是自主规划或任务成功率。
因此：

1. **任务因环境不满足而失败，不判 M1 失败**：没有目标方块、缺材料、地形不可达、怪物干扰等，
   只要 agent 正确识别原因、明确报告、不虚报完成、不破坏不变量（例如只一个执行者、停止仍有效），
   该次观察可以作为 M1 的**正向工作流证据**。
2. **只有工作流本身错了才判 FAIL**：例如终态播报两次、推进错误请求、能力来源不一致、
   虚报完成、两个执行者、停止等模型、迟到输出恢复动作。
3. **观测被破坏才是 INVALID**：死亡界面、断线、客户端未进世界、背包/目标被清空到无法观察，
   这类结果不判 PASS/FAIL，重跑。
4. **M1 不要求**：任务成功、自主规划、多步目标、模型质量、代码技能；这些在 M2/M3/M4 验。

### 2.6 证据记录

每条证据至少包含：阶段/主张 ID、提交、配置与版本、账号/服务器、初态、操作、观测、
结果、证据路径、判定。原件放 `runtime/logs/` 或 `runtime/` 下的 JSON；摘要写回
[`P1-CLIENT-TESTS.md`](P1-CLIENT-TESTS.md) 与阶段记录。

**进入前置**：M0-C2 基线可用于观测；若基线任务仅因环境不满足（无目标/地形/背包）而失败，

**出口依据**：P1 计划 M1：A04–A08 适用子集 + A31/F3 的真实宿主场景；新规划器/GUI 留到
