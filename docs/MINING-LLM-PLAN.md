# 挖矿机制优化方案：统一入口、逐格垫柱与 LLM 异常接管

> 日期：2026-10-10　状态：**方案（待排期实施）**。底座（`pillar` 原语、`pillar-up` 阶梯、四修复）
> 已落地并离线验证，已提交于 `f08c525`；真机证据与遗留问题见 §一。
> 当前设计：**Node 根据阶段进展与重复局面触发接管；LLM 多轮执行到一块目标矿被挖掉且对应产物入包；
> 常规路径继续使用确定性代码，LLM 只负责异常恢复。** 不预判地形复杂度，不建设覆盖全部采矿的统一行动计划。
> 统一入口（§5.6）、逐格垫柱（§5.4）及本文新增的接管机制均为待实施方案，不代表代码或验收已完成。
> 掉落物收集单独以 [`MINING-COLLECTION-PLAN.md`](MINING-COLLECTION-PLAN.md) 为准；
> 常规采矿与 LLM 接管必须共用其中的拾取目标、入包证据和失败处理，不维护两套拾取实现。

## 一、起因与真机证据（2026-10-10）

操作员在 `mc.example.com` 实测「挖钻石」，出现两类现象：**垫柱（pillar）只起 1 格左右**、
以及**脚本在复杂矿道里重复无效动作**。

| 证据 | 内容 |
| --- | --- |
| 尝试 1（异列：脚在 `(9,-59)`，矿在 `(5,-55)`） | `pillar steps=0/3 → 1/3`，重试 `0/2` 后 `place-failed`；期间 `dig refused at 9,-55 / 9,-54` |
| 尝试 2（同列：走到矿正下方 `(5,-59)`） | `pillar-up: rising 2 block(s)` 成功（脚 -59 → -57），随后 **`mined deepslate_diamond_ore @5,-55,171`、再挖 `5,-55,170`** |
| 反复动作 | 挖乱的竖井里出现 walkTo 原地 `stuck` 循环、direct 阶梯 `(5,-58)↔(6,-57)` 振荡、`unsafe tunnel waypoint … drop below` 把整个任务判 `danger` 停止 |

结论：**「不会在脚下放方块向上」已修复且真机生效**；剩下两个问题：

1. 升柱高度不可靠（只起 1~2 格）；
2. 宏技能在复杂地形会重复无效动作，现有确定性恢复阶梯仍可能耗尽，尚无 LLM 接管机制。

## 二、现状控制流（基线）

`mine_ore`（`src/skills/mining.js`）对每个矿的执行阶梯（`rungs`：`src/skills/mining.js:1059-1195`）：

```
tunnel → clear-retry → direct → pillar-up → flank
```

- `tunnel`：把 `quoteApproach`（`src/skills/miningPlan.js`）产出的台阶计划整段交给客户端
  `ClientActions.Tunnel`（`mod-client/.../ClientActions.java:985`）边走边挖。
- `pillar-up`（`src/skills/mining.js:1120`）：矿高于脚 ≥2/3 格时启用——Node 预清跳跃通道 →
  `body.pillar()`（`src/body/clientModBody.js:859`）→ 重试 `direct`。
- 底层 `ClientActions.Pillar`（`ClientActions.java:1307`）：每 hop = 起跳 → 腾空时对脚下地板顶面
  放置 → 落到新块上。
- 导航层已有共享到达判定 `withinGoalRange`（`src/pathfinding/planner.js:52`）与停滞护栏
  `stalled`（`src/pathfinding/navigator.js:224`）。
- LLM 工具面目前只有宏：`do_task` / `do_skill`（`src/llm/tools/registry.js:97/137`），没有块级工具。
- `LlmCore` 当前对话链路执行一批工具调用，再请求最终意图；没有持续到任务完成的恢复会话。
- `takeOre` 在拾取前就增加矿石计数，`collectDrops` 返回零也仍报告挖掘成功；
  以掉落实体消失判断拾取、以及向上拾取未接入垫柱的问题，详见独立收集方案。

## 三、根因分析

### 3.1 一次性预清 vs 4.5 格挖掘距离

`ClientActions.dig`（`ClientActions.java:341-360`）先检查玩家、世界和 gameMode 是否可用；在世界有效时：

- 目标已是空气 → 直接成功（`already gone`）；
- **目标中心距玩家 > 4.5 格 → 拒绝**（本轮有效世界里的超距坐标与该条件吻合；不能把所有
  `dig refused` 都解释为超距，后续回执必须保留具体原因）。

`pillar-up` 的预清循环一次性把 `脚上方 2 .. need+2` 的格子全挖掉，但：

- 脚在 `-59` 时，`-55` 的中心距 ≈ 4.51（dy=4.5 加水平偏移）→ 刚超限被拒；
- `-54`（dy=5.5）更不可能。

高处顶盖清不掉 → 后续 hop 的跳跃被顶住。尝试 1 的两次 `dig refused` 正是 `-55/-54`。

### 3.2 放置窗口被顶盖压缩到边缘

放置的物理条件：腾空时**脚底必须高于待填格顶面 ≥1.0 格**（否则方块与玩家自身碰撞，服务端拒绝）。

- 普通跳跃顶点 ≈ +1.25 格 → 天然窗口 ≈ 0.25 格；
- 若 `脚+3` 格处有实心（例：`-55` 的 deepslate 未清），头顶被卡在 -55 → 脚最高只到 **-56.8**，
  而放置需要 ≥ **-57.0** → 窗口只剩 **0.2 格（约 4 tick）**。

hop1 的头顶（`-57/-56`）预清成功，而后续跳跃仍可能被未清除的顶盖限制。
上述窗口宽度与 tick 数是根据方块几何作出的估算，尚未用逐 tick 服务端证据验证；
不能将 `place-failed` 的所有情况都归因于时序。改动应先消除未清净空，并记录每步放置与落地结果。

### 3.3 清障与升格没有交替递进

正确的人类做法：清掉够得到的 → 垫一格 → 再清更高的 → 再垫。
当前实现是"一次清到底（受 4.5 限制做不到）→ 连垫多格"，于是柱子在 1~2 格处停死。

### 3.4 宏技能的重复无效动作

`mine_ore` 把"先挖哪格、站哪、垫几格、从哪侧接近"全部写死在 JS 阶梯里。在被反复挖乱的竖井里：

- direct 阶梯要求"挖出新脚位后能跳上新块"，但乱空间里下方是空的（没有可站的台阶）→
  walkTo 报 `arrived` 却停在原地（宽容差）→ 反复 `stuck`；
- tunnel 的危险预检按"waypoint 下方悬空 >2 格"判定危险，对**上升**路线也生效 →
  整任务 `danger` 停止（2026-10-10 已用"上升豁免 + hazard 交给 pillar"缓解，但整类问题仍存在）；
- 失败的宏没有"停下来问大脑"的机制，只能在有限阶梯里穷举/重复。

## 四、优化目标与原则

1. **异常触发**：所有矿点先运行现有宏；Node 用实际进展与重复局面检测异常，不让模型或启发式先给地形打“复杂”标签。
2. **完整采集子目标**：接管成功要求同一目标矿的挖掘证据和对应产物入包证据齐全；一批动作结束不是接管结束。
3. **多轮短批次**：模型每轮提出少量有序动作，Node 逐步验证执行；失败截断余下动作，反馈后再决策。
4. **常规路径不重构为统一计划**：保留现有报价、阶梯、tunnel；只增加结果观测点和异常接管入口。
   接管用的短动作队列只在恢复会话内存在，不要求提前列出通往矿石的所有挖掘/放置格。
5. **共享执行与收集**：模型和宏复用同一套受控原语、取消机制、台账、拾取与入包验证；模型无自由代码、服务器指令或越权动作。

## 五、方案

### 5.1 接管专用块级操作

本阶段不把块级动作开放给普通闲聊，也不把每个动作注册成新的后台任务。
建议新增 `src/llm/miningRecoveryTools.js`，包含严格 Schema、参数说明和受控执行器，
只在有效 `recoveryId + taskId + goalId` 下可调用。普通聊天的 8 工具保持原能力边界。

| 操作 | 语义与上限 | 验证及返回 |
| --- | --- | --- |
| `mine_block(goalId)` | 挖当前锁定的目标矿一次；坐标由 Node 从目标记录解析 | 校验工具/距离/视线/权限，挖后复核并建立拾取阶段；返回 `mined` 与独立的 `acquisition` 状态，不自动宣称入包 |
| `dig_cells(cells)` | 按顺序清理 1..3 格，不包含隐式移动或重试 | 每格检查并复核；返回已完成、失败格、未执行格；每格计一个基础动作和一次地形修改 |
| `move_to_cell(stand)` | 去一个局部安全站位，默认每轴距当前脚格不超过 4 格 | 复用禁止自动挖掘的导航；有局部时限，返回实际落地位置；未拾取不因 arrived 判采集完成 |
| `pillar_up()` | 清障已通过后垫一格 | 复用 P4 的单格执行部分；本操作不隐含挖掉模型未声明的顶盖；返回实际升高与放置格 |
| `place_block(item, reference, face)` | 向合法面放一个明确支撑块 | 校验物品、触及、碰撞、支撑、权限，复核世界状态；不能直接指定任意空中坐标当成功 |
| `collect_target(goalId, standId?)` | 调共享收集器执行一次有界接近/确认 | 不隐藏十步挖路、升柱或再次调用 LLM；返回 `verified/pending/blocked` 和未收取原因；有移动时计入基础动作预算 |

只读信息通过每轮局面报告提供。确需更多局部数据时，模型可以返回 `inspect` 请求指定小范围切片，
由 Node 执行纯只读扫描；同一有效快照下重复请求同一切片不能无限刷新无进展计时。

`tunnel_to` 暂缓暴露：现有连续 tunnel 可在内部挖多格，权限/计划外格检查与中途回执还不足。
本轮接管用显式清障和局部移动即可，常规宏原有 tunnel 继续保留；以后补齐相关约束再单列验收。

动作处理器复用已有 Body/技能辅助函数，不从内部调用 `do_skill → TaskHub.submit`。
`dig_cells` 若碰到锁定目标矿，拒绝并要求走 `mine_block(goalId)`，防止绕过矿块计数与收集记录。
遇到其它符合本任务矿物集合的矿块也不得作为清障顺手挖掉；选其它合法格或停止报告，不能绕过 goal 锁定和 count 上限。
一批中挖掉目标后进入拾取阶段，剩余的挖矿/探索动作失效；下一轮以产物位置为目标，不继续寻找新矿。

### 5.2 Node 如何触发异常接管

#### 5.2.1 观测记录与阶段进展

新增 `src/core/miningProgress.js`。常规宏与恢复操作在**语义动作结束**时提交记录；
连续 tunnel 的实际挖格/到达航点也提供进度事件。不是每次按键、每个 tick 都算一次动作。
记录必须在动作前后读取有效新状态，包含：

```js
{
  taskId, goalId, mode, phase, actionId, action, args,
  startedAt, finishedAt, beforeRevision, afterRevision,
  beforeFeet, afterFeet, grounded, heldItem,
  relevantCellsBefore, relevantCellsAfter,
  expectedEffect, observedEffect,
  failure, reason, minedBlocks, placedCells, acquisition
}
```

beforeRevision/afterRevision 是拟新增的观测标识，不能假定当前快照已提供这些字段。
实现时同时保留成功读取时间、客户端世界会话及可用的 tick/版本；Node 本地递增序号仅用于回执关联，
HTTP 失败后返回缓存、会话变化或缺失关键格时必须标 stale/unknown，不能靠“序号加一”伪装有效新观察。

阶段与有效进展由 Node 计算，不能采信模型的 `progress:true`：

| 阶段 | 有效进展 | 不算进展 |
| --- | --- | --- |
| `approach` 接近 | 完成当前合法局部站位/航点，且不属于最近重复站位循环 | 原地跳跃、镜头变化、A/B 往返、只缩短瞬时欧氏距离 |
| `clear` 清障 | 为下一步净空/支撑条件服务的障碍格真实消失 | 挥镐、挖无关格、挖空已是空气的坐标 |
| `raise` 升格 | 放置支撑成功、同列落地高度真实增加 | 腾空时 y 增加、`steps:1` 但脚位不变 |
| `mine` 挖目标 | 本任务确认目标矿从指定类型变为挖后状态，记录一次挖掘 | 开始挖、旧快照为空气、仅动作接受成功 |
| `collect` 收产物 | 进入新的有效拾取站位可记局部进展；入包证据成立才记采集完成 | `moveTo arrived`、掉落实体消失、捡了清障石头 |

允许绕路暂时远离矿石；不要求每步距离单调缩短。阶段名改变本身不清空历史，
不断 `approach↔clear`、挖无关格或换参数不能延长无效循环的寿命。

#### 5.2.2 局面指纹与初始阈值

指纹包含 `goalId + phase + 落地脚格 + 必要相关格状态 + 当前工具/支撑材料可用性 + 目标/掉落状态`。
只对关系到当前动作前提的局部格子生成稳定哈希；时间戳、随机实体顺序、镜头朝向、无关怪物移动不计入。
负坐标用 floor，浮点位置需量化；同一格内会影响碰撞的站位偏差另保留，不用微小抖动产生“新局面”。

以下阈值是待实施默认值，要用验收场景校准，并由单一配置模块读取：

| 触发码 | 条件 | 决策 |
| --- | --- | --- |
| `same_failure` | 最近窗口内，相同目标/局面/动作签名/失败格出现 2 次已结束失败，期间无有效进展 | 阻止第 3 次原样重试；若有一个前提确实改变的本地恢复步骤，可至多尝试一次，再失败进入接管 |
| `position_cycle` | 最短 2..4 个站位/阶段组成的循环完整重复 2 次；地形、采集状态均无推进 | 不等待 40 次重规划，截断宏并接管 |
| `false_arrival` | 3 次动作报到达/成功但未实现阶段目标、稳定位置几乎未变化（<0.1 格） | 接管；与 navigator 的 stalled 互通，不能重复耗尽两轮阈值 |
| `no_progress` | 已结束至少 3 个尝试，累计主动执行时间 30 秒无阶段进展 | 接管；正常长挖、客户端确认等待等按动作时限管理，不因人物不动误报 |
| `ladder_exhausted` | 本地恢复阶梯耗尽，目标仍存在或有待收取产物，且动作所需条件未被硬性拒绝 | 直接接管，无须再制造一次重复 |
| `pickup_stalled` | 共享收集器已尝试不同可行站位仍未收到，或已到位但保持不可吸取状态 | 以 `phase=collect` 接管，继承已挖矿的记录，不重挖空气 |

保存最近 12 个完整语义记录；循环检测可存更长的压缩指纹。进度事件会更新计时，但预算不会重置。
动作仍在执行时观察到局部挖掘/航点推进，不触发上述“已结束失败”阈值；真正卡住由其动作超时结束后上报。
Mod 若不提供挖掘中间进度，按工具与方块预估时限加余量等待，不能仅用 30 秒人物位移判卡住。

#### 5.2.3 哪些情况不调用模型

- 人工界面、失焦、权限征询中：挂起执行并等待；这段时间不计主动无进展时间，不自动关闭界面。
- HTTP 失败、旧快照、维度改变、断线：中止当前动作并暂停；不把缓存当新观察交给模型继续施工。
- 死亡、操作员停止/替换、危险停止、明确权限拒绝：终止/暂停本目标；不能通过模型恢复解除限制。
- 背包无法接收产物、缺必需工具、没有任何已允许替代动作的材料不足：明确报告，不发空转模型请求。
- schema 错误、内部异常、未知失败：先诊断；不能把所有 `internal/unknown` 都当成地形策略问题。

仅凭 `failure='refused'` 不足以决定是否接管，必须区分权限拒绝、协议拒绝和超距等原因。
本地合法替代策略存在时可继续确定性恢复；LLM 不负责修网络、补权限或发服务器指令。

### 5.3 接管生命周期与防循环

#### 5.3.1 控制权与成功条件

```text
MACRO → 异常证据成立 → QUIESCE（取消当前动作、确认停止）
      → OBSERVE → MODEL → VALIDATE → EXECUTE_ONE → VERIFY
                                      ↑             │
                                      └─本批尚可继续─┘
      ← 未完成时下一批观察/模型决策 ← 本批完成或被截断
      → SUCCESS（目标挖掉且对应产物入包、人物稳定）→ 交回宏
      → BLOCKED / FAILED / CANCELLED → 停止任务并保留部分结果
```

整次接管属于原 `mine_ore` 任务，保留同一个 TaskHub/Brain 所有者；`recoveryId` 只是内部子会话 ID。
进入前停止并等待当前 Mod 动作落定；若停止未确认，不允许开始模型动作。
控制模式切换递增 `executionEpoch`，宏旧的异步回调即使返回也不能再发指令。
交回宏时再次更新 epoch，恢复后的宏显式取得新令牌；旧调用捕获的令牌不能被就地改成有效。
所有停止/释放操作核对自身 task/action 所有者，旧会话的 finally 不能解除新任务占用或停止它的动作。
模型等待期间角色站稳、无多余移动按键；危险/死亡/人工停止仍由本地监控处理。

锁定 `goalId`，其共享 `AcquisitionGoal` 结构定义于收集方案。默认不擅自换矿：
未挖目标被别人挖掉且没有可归因收获时，返回 `target_lost`；已挖目标则继续追踪产物，绝不重新采矿。

成功条件由 Node 判断：

```text
同一 goalId 有本任务确认的挖掘记录
AND 至少 1 个对应目标产物的入包证据达到收集方案的验证标准
AND 没有正在执行的动作，人物落稳且无当前危险
```

若接管从拾取失败开始，挖掘记录可来自本任务接管前的宏；旧任务/旧会话已经收过的矿产不能充数。
一次挖矿多掉几个产物时，首次入包可以达成接管里程碑，剩余可见产物仍保存在共享收集记录，
宏交接后先处理这些剩余产物再换矿。详见收集方案的 `verified` 与任务完成语义。
已 verified 的 goal 不再触发同一个“首次入包”接管；余料由宏按剩余预算处理，失败则 partial/停止，
避免恢复一进入就满足旧成功条件而反复交还。

一次清障成功、一格升高、一批动作成功、模型声称“完成”，都不能结束接管。
失败默认终止当前采矿运行并留下可读的部分结果及阻止自动重试的原因；不自动清空记录再让宏重试同一局面。
恢复需要操作员明确重试或一次新的有效任务；相关停牌只能由规定的控制入口解除。

#### 5.3.2 执行幂等与无效提案

- 动作签名为 `tool + 规范化参数 + goalId`，重复判断再结合局面指纹；同一工具不同有效净空下可以再用。
- 给每批/每步分配唯一 ID。HTTP 请求超时、模型响应重放、重连后看到相同计划时，不直接重放世界修改：
  先读动作回执/世界状态确认是否已经发生，不能重复挖矿计数或重复垫一格。
- 在相同相关局面下，模型再次提出已经证明失败的同一动作，Node 返回 `repeat_rejected` 而不执行；
  只改 JSON 顺序、视角或无关参数不算新策略。连续 2 次无有效提案则以 `no_valid_recovery` 退出。
- 原始结果先入历史再进行下一轮；部分挖掘/放置即使动作整体失败也必须记账，不能只记录成功批次。
- 净空改变、工具切换、站位或支撑真实改变时，可以重新评估旧动作；材料被消耗但几何没改善不自动算进展。
- 沿用 navigator stalled 和恢复阶梯限制；接管不重置父任务截止时间、地形修改总账或采矿数量上限。

### 5.4 迭代式清障垫柱（确定性增强，立即可落）

**现状与修改目标。** `mining.js` 的 `pillar-up` 目前在起点快照上清理 `脚+2 .. 脚+need+2`，
不检查每次 `digAt()` 是否成功，随后 `pillar(need)`；失败后又用 `need-1` 重跑并覆盖上次结果。
这同时存在超距预清、带顶盖起跳、部分成功高度丢失三个问题。改成每轮只处理一次升格：
**刷新 → 确认下一跳净空 → 清障并复核 → 垫一格 → 核验落地 → 累加实际高度**。

#### 5.4.1 修改位置与职责

| 文件 / 位置 | 具体修改 |
| --- | --- |
| `src/skills/mining.js`：`pillar-up`、`digAt`、`takeOre`、任务返回值 | 删除一次预清与整段递减重试；调用逐格升柱执行器；清障失败保留结构化原因；累计升格结果并正确计矿 |
| 新增 `src/skills/pillarUp.js`（内部辅助模块，暂不注册 LLM 工具） | 实现有预算的单格循环；接收目标、截止时间、取消信号，以及受控清障/取矿/记账回调；供后续 P1 复用 |
| `src/body/clientModBody.js`：`pillar` / `awaitAction` | 只将明确的动作回执视为完成；缺失 `steps` 不得默认等于请求数；清除旧回执，核对动作名并返回实际值 |
| `src/core/permissionGate.js` | 为单格 `body.pillar(1)` 的实际放置接入现有权限判定、任务内征询与 selfPlaced 记录，避免连续动作绕过 `place` 闸门 |
| `src/core/taskHub.js`、`src/skills/registry.js`、调度适配层 | 透传任务专属取消信号；停止、替换、死亡和超时后禁止技能再发下一条动作 |
| `src/body/mockBody.js`、相关测试脚本 | 用受距离、净空、库存、落地约束的场景验证，不能仅靠模拟器直接修改 y 判成功 |
| `ClientActions.java`：`Pillar`（按协议验证结果修改） | 保留一格升柱控制器及每步最多 3 次跳跃；若回执缺少定位字段，补充本步起点、落点、实际放置格和失败原因 |

策略循环放在 Node；Mod 只负责可靠完成一格的起跳、放置和落地。若修改 Java，必须重编译、安装并重启客户端后再做真机验收。

#### 5.4.2 每格执行规则

1. **固定本次升格终点。** 以阶梯开始时的脚格与目标矿计算 `goalFeetY`：同列停在矿下两格，
   异列停在矿下一格；沿用当前单次最多 16 格的预算。后续用 `goalFeetY - 当前脚格.y` 算剩余量，
   不把旧 `need` 再当作新请求高度。每轮先尝试已可触及且无遮挡的目标矿，挖掉后进入共享收集流程，
   不能将“够得到挖矿”当成“已经能拾取”。用于高处掉落物接近时，终点改由收集器提供的安全拾取站位决定。
2. **读有效新状态。** 每轮及每次清障后强制刷新，要求世界可用、位置和方块扫描有效、玩家已落地。
   HTTP 失败后沿用的缓存不算刷新成功；缺少必要格子、玩家横移到另一列、脚下失去实体支撑时退出，
   不将未知方块当空气，也不自动换列继续垫。
3. **只清下一跳必需的净空。** 对普通完整方块，脚为 `(x,y,z)` 时，检查本列 `y+2` 与 `y+3`，
   按从低到高处理实心块；`y+3` 用来消除头部在跳跃顶点被盖住的问题。`y+4` 留待升一格后处理，
   不再预清全部目标高度。半砖、特殊碰撞箱或无法确认的 Mod 方块保守返回原因。
4. **距离、工具与权限逐格验证。** 挖掘前按 Mod 当前口径计算玩家位置到方块中心的三维距离，
   超过 4.5 格不发送 dig；调用现有工具选择、落沙/贴水/岩浆检查及受权限保护的 `body.dig`。
   `digAt` 返回失败时立即退出本轮，不能继续起跳；返回成功后也要刷新确认该格已经可通行。
5. **目标矿不作为普通清障块处理。** 必需净空中若包含本次目标矿，走 `takeOre` 的挖矿、计数和拾取流程。
   取不到则返回 `out_of_reach/occluded`，不能跳过它后强行起跳，也不能挖掉后漏记为“目标丢失”。
6. **逐格装备与放置。** 每轮重新选择背包中的可用支撑块；排除沙、砾石、容器和不可确定的支撑物。
   清障后切换支撑块并核实手持，再发且只发 `body.pillar(1)`。下一轮清障重新选镐；回归取矿时也要换回镐。
   支撑块耗尽返回 `no_material`，不空手跳跃。
7. **核验实际完成。** 等动作结束，再读新快照：保持同列、脚格恰好升高 1、已经落地、旧脚格变成支撑块。
   `/progress` 的 `action/done/failed/steps`、位置、方块和库存变化共同作为证据；单独 `ok:true` 或
   `steps:1` 不足以完成计数。服务端状态可在单步剩余预算内短暂复核，不发送第二次放置来“催确认”。
8. **部分结果不丢失。** 每完成一格立即累加 `risen/placedCells`。后续失败返回累计值及失败位置，
   禁止旧的 `pillar(need) → pillar(need-1)` 重试。回执矛盾、没有位移或一次增加多于一格时停止，
   保留观测到的位移；不伪造成功，也不把之前完成的格数清零。

示意流程（所有动作仍经过现有技能/Body 边界）：

```
固定 goalFeetY，累计 risen = 0
while 未达到 goalFeetY:
  检查任务取消 / 截止时间 / 有效新快照 / 落地 / 危险 / 本列支撑
  若目标可直接取到：按取矿流程执行并返回
  逐格检查并清理本列 y+2、y+3；每格成功后复核并记账
  再检查取消与危险，装备支撑块，核准这一格的放置权限
  result = pillar(1, timeout = min(单步上限, 任务剩余时间))
  核对回执与新世界状态；失败则带累计结果退出
  risen += 1，记录 placedCells，进入下一轮
达到目标高度后回到正常接近 / 取矿流程
```

#### 5.4.3 预算、终止与回执

- 沿用 `mine_ore` 的总 `deadline`，单格动作上限建议 8 秒；净空检查、挖掘、征询、放置和结果复核
  全部消耗同一任务预算。没有足够剩余时间就结束，不在每轮重置十分钟计时。
- 清障继续计入原 `DigLedger`；计划外格子记 `extra`，下一格将超过 `maxExtraDigs` 时在动手前拒绝。
  不通过重新创建台账抹掉已发生的修改。放置另记 `placedCells`，不冒充挖掘数量。
- 岩浆、落沙、进水、怪物、无支撑、拒绝权限、取消和预算耗尽均需明确终止。
  “上升 waypoint 下方悬空”的特例不能豁免当前落脚点支撑及上述危险检查。
- 取消状态属于任务自身；不能用全局 `owner-stop` 判断取消，因为该停牌允许新显式任务。
  取消信号须在每个 await 返回后、下一次副作用前检查；已取消任务不得进入 `direct/flank` 继续动作。
  `TaskHub` 若等待旧任务退出超时，应拒绝启动替换任务并保留占用状态，不能让两个执行器继续抢同一身体。
- 一次 `pillar(1)` 已包含 Mod 内部的有限跳跃重试；Node 收到失败后不自动原样重发。
  普通无路失败可带新位置交给后续阶梯，危险、拒绝、取消与预算耗尽不可被普通换路吞掉。
- 放置权限从当前物品、支撑面和待填格生成；`ask` 等待后重新验证位置与物品，获准的旧坐标不能用于新坐标。
  正常运行必须走权限层；测试缺少权限上下文的情形应显式构造，不能让生产路径静默跳过。

内部结果建议保留：

```js
{
  ok, failure, reason, cell, block,
  requested, risen, remaining, start, end,
  clearedCells, placedCells, minedTarget, interrupted, elapsedMs
}
```

`failure` 复用现有枚举；如 `no-headroom` 对应 `occluded`、材料不足对应 `no_material`、停止对应
`interrupted`，协议缺失或状态矛盾可用 `internal` 配合具体 `reason`。辅助模块的 `ok` 只表达其自身
阶段是否完成，矿石是否被挖掉由 `minedTarget` 和主技能的 `mined/minedAt` 表达，产物是否入包由共享
acquisition 证据表达。最终回执和日志必须保留升了几格、在哪里失败，不能只剩一句 `no_path`。

### 5.5 常规路径与接管路径的关系

```
所有矿点 → mine_ore 确定性宏 → 共享收集器 → 完成本矿采集 → 下一矿
                │                  │
                └── Node 确认异常 ─┘
                         ↓
           停稳 + 保存目标/台账 + 建立恢复会话
                         ↓
             观察 → LLM 短批次 → 验证执行
               ↑                    │
               └─未入包且预算允许───┘
                         ↓
          首个对应产物入包 → 同一任务内交回宏
          失败/停止/超预算 → 保留未收取记录并停止
```

不根据“复杂环境”预先分流；图中的 LLM 路径只由执行异常触发。
共享收集器是两条路径相同的底层能力，不是新的全局行动规划器。

### 5.6 统一挖矿入口（先于 LLM 块级工具）

> **规划器边界提示（2026-10-14）**：本节描述的入口统一发生在**请求解释层**；真正决定"何时自动去挖矿"
> 的是**自主规划器**（`slowLoop → decide() → MineOreTask` 适配器）。规划器侧的已知问题——
> `MineOreTask.progress()` 每次返回新对象导致规划器的零进展停牌对其完全失效（P3）、零收获矿石运行
> 返回 `ok:true` 因而也不进失败罢工（P4）、停牌粒度是任务名而非目标（P5）——记在
> [`PLANNER-REFACTOR.md`](PLANNER-REFACTOR.md)。**不要**把这些当作本方案（技能层）的缺陷来修。

**目标。** 同一目标、数量与采矿参数从不同入口进入时，应得到相同的目标集合和执行器：
矿石走 `mine_ore`；石头、泥土、沙等普通材料保留 `MineBlockTask`。统一的是请求解释和执行选择，
不把所有材料都强行改成寻矿，也不在纯步行 A* 中开启挖掘。

#### 5.6.1 当前遗漏与覆盖范围

| 入口 | `f08c525` 的状态 | 本批修改 |
| --- | --- | --- |
| `!mine`、面板/HTTP `mine` | `commands.js` 直接构造旧 `MineBlockTask` | 进入公共分流器，矿石提交新技能 |
| 原生工具 `do_task(task="mine")` | `actuators.doTask` 只取 `blocks[0]`，再派发旧命令 | 保留完整数组，直接调用公共分流器 |
| LLM JSON `task:mine` | `LlmCore.execute` 单独按 `_ore` 重定向 | 删除重复判断，交公共分流器 |
| 自然语言兜底 | `fallbackRouter` 自己按矿石后缀选技能 | 只负责抽取意图/数量，目标分类共用同一规则 |
| `do_skill("mine_ore")`、JSON skill、`run-skill.js mine_ore` | 可以直接运行，但 `ore/block` 和变体归一仍是独立实现 | 在技能边界也调用同一个纯归一函数，防止直调绕过 |
| `!goal`、启动 `--goal` | 分别在 `commands.onGoal`、`index.applyGoal` 里造旧任务；CLI 泛“挖”还可能先匹配石头 | 复用目标解析，明确矿物优先于泛采集词，不能把“挖铁”解释为挖石头 |
| 自主采铁、内部 `ctx.mine` | `brain.decide` / `index.js` 仍直接创建旧任务 | 共用请求归一与执行选择，使用适配任务保留 Brain 的所有权和优先级 |

直接调用 `mine_ore` 时，普通材料目标应明确拒绝为 `bad_argument`，避免技能名与行为不一致；
混合“矿石 + 普通材料”的一次请求也拒绝并要求拆分，不能只保留矿石或第一个目标。

#### 5.6.2 公共接口与参数规则

新增 `src/core/miningRequest.js`：只做纯函数解析，返回
`{ok, kind: 'ore'|'material', blocks, count, params}` 或结构化 `bad_argument`；不调用聊天、LLM、
Brain 或 Body。新增 `src/core/miningDispatch.js`：负责校验、调度与执行器选择，避免
`commands → actuators → commands` 循环依赖。模块名为建议命名，职责边界为验收要求。

统一规则如下：

1. 接受各入口已经声明支持的形状：命令的单名/逗号串、`do_task` 的字符串数组、技能的 `ore/block`
   字符串；入口先按自身 Schema 校验，再转成公共目标数组。不得为迁就解析而放松工具的未知参数拒绝规则。
2. 去空白、去重；只归一 `minecraft:` 前缀，保留其它 namespace。`iron/diamond/gold/coal` 等别名
   从同一份表展开。原版主世界矿石的普通/深板岩对应使用显式表或注册表核对，不对所有 `_ore` 盲目加前缀：
   `nether_quartz_ore/nether_gold_ore` 不应生成不存在的深板岩变体，Mod 矿石也不得被改成原版方块。
   矿石分类以原版矿石表和已有 Mod 知识为准，`_ore` 后缀只能作提示，不能独自证明方块存在或可以挖。
3. `diamond_ore` 自动包含其真实存在的深板岩变体；显式 `deepslate_diamond_ore` 保持精确目标。
   多目标数组保留全部项与顺序。最终技能匹配必须是归一名称的精确集合匹配，不能用缺少起始锚点的正则
   意外匹配别的矿石。未知目标明确报错；已知 Mod 矿石还需通过已有知识/工具策略，无法确认不猜测挖掘。
4. `ore` 与 `block` 同时出现时，归一后相同可接受，不同则报 `bad_argument`；不再静默优先取 `ore`。
5. 显式 `count` 必须是 1..256 的整数；0、负数、小数、NaN、超过上限均拒绝，不能用 `Number(x) || 8`
   偷换成默认值。普通命令和 `do_task` 缺省仍为 8；已有目标规则的缺省数量在进入公共层前明确传入。
   直接 `mine_ore` 未给 count 时保留“扫描/时间预算内持续采矿”的既有含义。
6. 矿石 `count` 定义为实际挖掉的目标矿石块数；不得套用旧命令的 `count+2`，不得用掉落物数量充数。
   清障块不计矿石数，目标产物数量由共享收集器另报。达到 count 后不再挖新矿，但必须处理尚未收取的产物；
   “数量达到、部分未收取”应是部分完成，不得宣称全部采集成功。普通材料保留原计数语义。
7. `maxXZ/maxY/maxMs/maxApproachDigs/maxExtraDigs` 等技能参数经 Schema 校验后原样传递。
   未采足时必须返回实际数量及停止原因，不能只因任务已受理就向玩家宣称“挖完”。

#### 5.6.3 调度、取消与回执

- 玩家命令、面板、LLM 工具/意图的矿石请求，在改动世界或替换旧任务**之前**完成名称、参数和能力校验，
  然后只提交一次 `TaskHub`；立即返回同样形状的 `{ok, accepted, async, taskId}`。
  非法新请求不能取消正在执行的合法任务。不要沿用 `ChatController.runSkill` 等待长技能完成的同步路径。
- 本批将显式矿石请求统一为 TaskHub 的“新请求替换旧请求”语义；`!mine` 不再因自身走旧 Brain 队列
  而与 `do_skill` 表现不同。保留死亡/暂停等停牌规则，`owner-stop` 仍允许操作员发起新显式任务。
  调用来源、speaker、优先级通过局部参数传递，不在长异步任务中读取可被另一条消息覆盖的 `dispatchSource`。
- 自主采铁使用新增 `MineOreTask` 适配器：由 Brain 调度，在已有任务所有权内调用同一 `mine_ore` 执行器；
  不从该任务内部再提交 TaskHub，否则会抢占自己。`ctx.mine` 也要明确“已持有任务所有权”的内部执行契约；
  外部请求只能走提交入口。适配器的取消/超时必须传到技能，而不能只结束外层 Promise。
- 适配器保留 `progress` 与 `mined/ledger/failure` 等结果；必要时修正 `Task.normalizeResult` 当前只保留
  `ok/reason` 的行为，并补旧任务兼容用例。自主任务结果不触发玩家任务完工播报。
- TaskHub 与 Brain 共用任务取消信号，按 §5.4.3 在动作边界检查。受理、完成、失败、替换各记一次事件；
  玩家一次请求不能既启动旧任务又启动新技能，LLM 工具执行后也不能因最终意图再重复派发同一任务。
- 公共执行器直接调用技能层；`do_skill('mine_ore')` 可调用公共提交层，但执行器不得再回调 `do_skill`，
  以免递归提交。材料请求继续交旧任务，不能以新矿石路径的失败为由悄悄回退到旧矿石任务。

修改文件应包括 `commands.js`、`llm/tools/actuators.js`、`llm/index.js`、`fallbackRouter.js`、
`skills/mining.js`、`index.js`、`brain.js` 及新增公共模块/任务适配器；`expandBlockNames` 可保留导出作
兼容包装，但别名规则只维护一份。更新工具说明、`!help` 和相关用例，使模型与操作员看到的计数语义一致。

### 5.7 LLM 调用条件、频率与批次执行

#### 5.7.1 事件驱动，不按固定秒数调用

| 事件 | 是否调用 | 后续动作 |
| --- | --- | --- |
| 首次异常、宏动作已停止且状态有效 | 是 | 用当前阶段与失败历史生成首批，首批限 1 个基础动作 |
| 一批执行完，采集里程碑未达成 | 是 | 汇总最新位置/地形/收集状态，决定下一批 |
| 动作失败或实际后置条件不符 | 是 | 截断本批后续动作，记录已完成部分；确认停止后再调用 |
| 下一动作的必要前提改变 | 是 | 不执行失效动作；若变化已构成危险/权限拒绝，直接停止而非调用 |
| 模型返回有效 inspect 请求 | 读完后是 | 返回局部切片；这也消耗调用预算，重复只读不延长执行预算 |
| 目标矿已挖掉但未入包 | 是，若正由 LLM 接管 | 进入 collect 阶段，继承同一 goal；不恢复宏继续挖 |
| 当前动作正在正常进行、服务端状态确认中 | 否 | Node 250..500ms 级进度监控，按动作截止时间处理 |
| 已达到采集里程碑并站稳 | 否 | Node 直接结束接管；如需玩家完工措辞，独立只读播报不能再派动作 |
| 界面/权限等待、失焦、停止、死亡、断线、危险 | 否 | 等待或中止；不以多问一次模型代替必要条件 |

一轮模型调用生成一批；正常批次执行期间不调用模型，不并行安排身体动作。
批次默认最多 3 个基础动作；`dig_cells` 挖两格加一次垫柱正好为 3 个。
首次接管或上一批失败后的首批限制为 1 个；连续两批均符合预期后恢复到 3 个。
未来可经实验提高上限至 5，但本轮不自动开放；“1..3”是批大小，不是整个接管只做 1..3 步。

长挖掘不会因超过某个 LLM 调用间隔被打断。动作超时应含合理挖掘时间与网络确认余量，
到期先 stop 并复核现场，才把失败交模型；无法确认停止时不得进入下一批。

#### 5.7.2 模型输入与输出契约

建议新增独立 `MiningRecoverySession`，复用 `LlmClient` transport，但不直接调用
`LlmCore.handle`、闲聊兜底路由或“工具轮后再派最终意图”的流程，避免一次恢复生成两个任务。
首版采用**受 Schema 约束的短批次 JSON**，动作名来自 §5.1 专用注册表；未来换原生 tool calling
也必须通过相同批次校验器，不能收到多条 tool_calls 就无条件执行全部。

输入包括：锁定目标和当前阶段、当前安全站位、局部三维方块/剖面、有效候选拾取站位、工具/库存/耐久，
最近 12 条压缩动作回执、最近失败签名、累计修改台账、AcquisitionGoal 状态、剩余预算。
`spatialGrid` 可作俯视辅助，但不能替代竖井高度和净空数据。
局部信息默认以人物和目标/掉落点为中心截取，明确范围和 unknown；超出报告的坐标先 inspect，不能猜空气。
背景说明和目标不能因截断历史而消失；权限与工具 Schema 置于固定系统约束中，环境文本仅作为数据。

响应形式示例（坐标仅示意，非授权的固定动作）：

```json
{
  "recoveryId": "r1",
  "goalId": "g1",
  "basedOnRevision": 42,
  "decision": "execute",
  "steps": [
    {
      "id": "r1-b3-s1",
      "tool": "dig_cells",
      "args": {"cells": [{"x": 5, "y": -57, "z": 171}, {"x": 5, "y": -56, "z": 171}]},
      "purpose": "clear_next_jump",
      "expected": {"type": "cells_passable"}
    },
    {
      "id": "r1-b3-s2",
      "tool": "pillar_up",
      "args": {},
      "purpose": "reach_pickup_stand",
      "expected": {"type": "grounded_one_block_higher"}
    }
  ]
}
```

`decision` 只允许 `execute/inspect/stop`；stop 带可读原因但不能声称 verified。
整型坐标、枚举、数组长度、物品名称、未知参数、步骤 ID 唯一性、goal/recovery 一致性都要校验。
`purpose/expected` 使用有限枚举，不接受表达式、脚本、任意 URL；Node 独立推导并核验真实前后条件。
批次 ID 最终由 Node 分配/绑定，模型填写的 ID 不构成新的权限或控制权。

Schema 的首版约束至少包括：

| 字段 / 分支 | 契约 |
| --- | --- |
| 通用字段 | 必须回显 recoveryId、goalId、basedOnRevision；所有对象拒绝未知字段；Node 校验当前会话，模型不提供 taskId/epoch 来申请权限 |
| execute | 必须有非空 steps；不能同时带 inspect 请求；按展开后的基础动作数校验本批上限 |
| inspect | 必须有 inspect 对象，内含 center、radiusXZ、yMin、yMax；无 steps；center 来自已观察局部范围，默认半径 <=4、垂直层数 <=7、总格数 <=567；超范围拒绝，缺失格保留 unknown |
| stop | 必须有有限长度 reason，无 steps/inspect；映射为未恢复退出；仅 Node 可根据证据设置 recovered |
| purpose | 只允许 clear_next_step、clear_next_jump、reach_ore_stand、reach_pickup_stand、support_next_step、mine_target、collect_target |
| expected.type | 只允许 cells_passable、at_safe_stand、grounded_one_block_higher、support_present、target_mined、acquisition_checked；所需目标由 Node 据参数补全 |
| 基础动作计数 | mine/move/pillar/place 各 1；dig_cells 按实际待尝试格逐格扣；collect_target 最多一次移动，移动计 1；纯观察不计身体动作，但计调用/时间预算 |

上述例子表示连续两批单动作成功后的第 3 批。工具自动装备合适镐/支撑块属于执行前提，
仍要记录耗时与结果；不能在“装备”名义下附带获取材料、隐式清障或额外移动。
单个身体操作的截止时间取工具合理上限和父/恢复剩余时间的最小值；局部移动首版上限 8 秒，
普通挖掘按工具/硬度估时并加确认余量，不对全部方块硬套 8 秒。未执行的后缀不扣已执行动作数，
但整批静态检查时必须预留其上限；失败的已尝试动作仍扣账。

先静态验证整批形状及总预算；执行到每一步时再验证动态前提，不能要求“移动后才够得着”的后续动作
在批次起点就已可达。每步成功后刷新；前一步失败、目标切换到收集阶段或环境改变时截断失效的剩余步骤。
返回给模型的结果明确分成 `executed/failed/notExecuted`，并含实际变化，不笼统写“批次失败”。

模型响应回来时检查 task 所有权、executionEpoch、目标和相关格是否仍满足前提；
快照 revision 增加本身不导致失效，只有与动作相关的变化才需重规划。取消后的迟到响应仅记日志，禁止执行。

### 5.8 配置、成本与失败降级

建议新增 `config/agent.json → miningRecovery` 配置，由公共模块读取；下表是首版建议值，非已上线配置。
接管执行仍受父技能 maxMs、原地形预算和全局模型额度约束，所有上限取更严格者。

| 配置 | 初值 | 作用 |
| --- | --- | --- |
| `enabled` | false，验收后显式开启 | 关闭时仍记录异常，确定性恢复耗尽后诚实失败，不调用模型 |
| `historySize` / `sameFailureLimit` / `falseArrivalLimit` | 12 / 2 / 3 | §5.2 观测与重复条件 |
| `noProgressActiveMs` | 30000 | 主动执行时间；不包括人工等待、模型推理时间 |
| `maxActionsPerBatch` / `maxCellsPerDig` | 3 / 3 | 多格挖掘按实际格数计基础动作；不能利用一个大工具绕预算 |
| `maxCallsPerSession` | 12 | 含 inspect 后的调用、无效响应修复及网络重试 |
| `maxSessionMs` | 180000 | 从接管开始的墙钟上限；模型/人工等待也不能无限延长本任务 |
| `maxSessionTokens` | 32000 | 输入、输出及服务商计费推理 token；与全局 dailyTokenBudget 共用记账 |
| `maxPrimitiveActions` / `maxPlacedBlocks` | 32 / 8 | 接管累计操作和放置限制，失败尝试也占动作预算 |
| `modelTimeoutMs` / `maxOutputTokens` | 15000 / 2000 | 实际调用受剩余时间和 token 预算裁剪 |
| `maxInvalidRepairs` / `maxRepeatedProposals` | 1 / 2 | 非法 JSON/Schema 可反馈修复一次；重复无效提案达到上限即停 |

共享模型并发闸门：恢复与聊天共用现有并发限制和 token 账本，不另开一个逃逸通道。
控制命令不等待模型闸门；普通对话可以等待，但不能通过另一轮工具调用同时操纵同一身体。
`LlmClient.complete` 当前只有内部超时 AbortController，需要支持外部取消信号，并与超时信号正确合并。
每次发送前预留估计输入加最大输出额度，返回后按 usage 结算；usage 缺失保守记账并标记估算，不能按零计费。
响应已在网络中发生的费用仍计入，即使它因任务取消而未执行。

没有 key、额度不足、模型超时/不可用时，不退回正则路由重新启动 mine；
停止本次恢复，保留 `minedBlocks/collectedItems/pendingDrops/risen`，返回 `recovery_unavailable` 或具体预算原因。
硬预算到期后允许停止及只读核验，不再启动“收尾捡一下”的新移动、挖掘或放置。

### 6.1 A：统一入口的离线验收

## 七、安全与边界（不可回归）

- `/register` 四道闸门、dig/place/useOn 权限闸门、`ask` 征询不变；

## 八、风险与取舍

| 风险 | 缓解 |
| --- | --- |
| 接管 token 成本 / 延迟上升 | 事件触发、短批次；调用数/时间/token 共限；正常宏无需恢复模型调用 |
| LLM 选错格或反复尝试 | 逐步核验相关前提、权限与预算；局面和动作联合护栏；不依赖模型自报进展 |
| 宏与恢复的收集实现漂移 | 共用 AcquisitionGoal、执行原语和验证函数；双模式使用同一批测试夹具 |

| 检测误触发或漏触发 | 按阶段评估、剔除人工/网络等待，保存轨迹回放校准阈值；先受控启用 |

## 九、已定默认值与后续调优边界

1. 首版使用异常接管；不按地形复杂度预分流，不要求全部矿点预生成动作计划。
2. 单批 1..3 个基础动作，默认最多 12 次模型请求；接管目标是当前矿的首次对应产物入包。
   调用/时间/token 等完整默认值集中在 §5.8；它们是上限，不保证在父任务剩余预算内都能用完。
3. 接管失败默认停止当前任务并报告部分结果；自动跳矿、自动放弃余料继续不在首版。
4. dig_cells 单次最多 3 格且受动态批次限制；玩家方块依既有 deny/ask 权限，模型无权自行许可。
5. 阈值与批大小可根据回放、误触发率、取得首个产物的耗时和成本调优；改默认值要重跑对应边界用例，
   不把“增大重试次数”当作循环问题的修复。
6. §5.4 先覆盖 clientmod 与 MockBody；后续是否复用到 recovery.climbOut、扩展 mineflayer 物理脱困、
   增加 tunnel_to，分别另立范围与验收。当前方案可据上述默认值开始实现，无需悬置等待额外策略选择。
