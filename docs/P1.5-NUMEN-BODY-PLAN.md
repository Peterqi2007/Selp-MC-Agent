## 1. 定位与结论

P1.5 是**身体层迁移**，不是 P2 的子阶段，也不改 Pi/DSH 大脑的运行时与语言主流程；只增加 body/tool adapter。P2 的 B0/B1 继续并行，不等待 P1.5；P2 B2 再决定是否消费 `NumenBody`。

它要回答一个问题：

> 能否把“Node 通过 Forge 客户端控制 mod 驱动真人玩家”替换为
> “Node 通过 Numen 驱动服务端假玩家”，同时让语言脑和动作脑继续工作？

本文的结论：

1. **聊天读写不需要改 Numen 本体。** 新增一个 Forge 客户端 bridge，把 vanilla chat 的读/写暴露为 HTTP；Node 的 `Body.readChat()` / `Body.chat()` 接到它即可。
2. **基础动作调用不需要改 Numen 本体。** Node 直接走 Numen 内置 MCP（`127.0.0.1:8765/mcp`），用 `tools/call` 调身体工具。Numen core 注册 34 个工具；MCP 默认隐藏 `todowrite`/`load_skill`，因此 `tools/list` 暴露 32 个引擎工具 + 3 个管理工具（`list/create/delete_companion`）。
3. **严格终态/硬停止需要两处小补丁**，都在 `numen-api`，不在 Numen core 的 34 个工具/寻路/任务实现里：
   - P-01：外部调用者的任务终态结果（约 150–220 行；含 server→client 结果回传）；
   - P-02：外部硬停止（约 40–60 行）。
4. **无 owner 客户端纯专服不做。** 当前 Numen 的 MCP、工具注册表、chunk 加载、复活都依赖 owner 客户端在线；这是架构约束，不是 bridge 能补的。
5. **截图、原始键鼠、keybinds、菜单 slot 点击、CodeSkills 生成输入脚本不保留。** Numen 是服务端假玩家，没有客户端相机和键鼠；这是范式差异，必须写进验收和非目标。

因此 P1.5 的范围是：

```text
语言脑（Node）  ── Body.readChat/chat ──┐
动作脑（Node）  ── NumenBody ── MCP ────┤
                                        ├── Numen 服务端假玩家（感知/执行）
ChatBridge（Forge 客户端）── vanilla chat ┘
```

P1.5 不改变 P2 的 `ActionBrainRuntime`；它只提供一个可被 P2 `GameControlPort` 复用的身体服务。

## 4. 目标架构

### 4.1 组件

| 组件 | 语言/位置 | 职责 |
| --- | --- | --- |
| `NumenBody` | Node，`src/body/numenBody.js` | 实现 `Body`；聊天走 bridge，动作走 MCP |
| `NumenMcpClient` | Node，`src/body/numenMcpClient.js` | MCP JSON-RPC：初始化、列工具、调工具、列/建 companion |
| `NumenChatBridgeClient` | Node，`src/body/numenChatBridgeClient.js` | bridge HTTP：`/chat`、`/world`、`/health` |
| `NumenTaskTracker` | Node，`src/body/numenTaskTracker.js` | 任务受理、轮询、终态推断、去重、`stop` |
| `ChatBridge` | Java，`mod-numen-bridge/` | Forge 客户端 mod：捕获 vanilla chat、写 chat、提供 `/world`、`/health` |
| Numen + numen-api | 用户安装 | 服务端假玩家、34 工具、MCP、任务执行 |
| 现有语言/动作脑 | Node | 不改主流程；只接 Body/MCP |

### 4.2 数据流

```text
玩家在 vanilla chat 输入
  └─ Forge ClientChatReceivedEvent
       └─ ChatBridge 环形缓冲（seq/at/text）
            └─ GET /chat?sinceSeq=  ← NumenBody.readChat()
                 └─ ChatListener（现有解析/去重/地址通道）
                      └─ 语言脑

语言脑回复
  └─ Body.chat(text)
       └─ POST /chat  → ChatBridge
            ├─ 默认：Minecraft.gui.getChat().addMessage("Companion: ...")（仅 owner）
            └─ 可选：SpeechBubblePayload（附近玩家气泡；N1 不做）

动作脑 mc_step / P2 GameControlPort
  └─ NumenBody.execute
       └─ NumenMcpClient.tools/call
            └─ Numen 服务端 onServerCall
                 ├─ 同步工具：立即返回结果
                 └─ 异步工具：返回 task_id
                      └─ NumenTaskTracker 轮询 task_status / 观测
                           └─ 终态（P-01 后为结构化结果）
```

### 4.3 为什么不做无客户端

- `NumenMcp.initClient()` 只在 `NumenForgeClient.registerReloadListeners` 调用；专服没有 MCP。
- `NumenActuator` 的每个方法都 `Minecraft.getInstance().execute(...)`，必须客户端进程。
- `CompanionTickDispatcher.tick()` 的 chunk pad 刷新条件是 owner 在线；owner 离线时 companion 不保 chunk，任务无法稳定执行。
- `Companions.tickRespawns()` 在 owner 离线时跳过；死亡恢复也不会发生。
- `/numen player summon` 用 `getPlayerOrException()`，必须有一个在线玩家执行。

要做无客户端，必须改 Numen 的 owner/chunk/result/MCP 架构，属于另一个量级的项目；P1.5 明确不做。

### 5.3 Numen 补丁（仅在 N3/N4 需要时）

补丁只改 `numen-api`，不改 `numen-core` 的 34 个工具、寻路、任务实现。

| 补丁 | 文件 | 改动 | 行数 | 需要阶段 |
| --- | --- | --- | --- | --- |
| P-01 external task result | `.../task/LlmTaskChain.java`、`.../agent/tool/ServerToolTransport.java`、新增 `.../client/agent/ExternalTaskResults.java`、`.../api/NumenActuator.java`、`.../mcp/server/McpServer.java` | server：`drainResults()` 对 external async 不再 `continue`，把终态包成 `TaskResultPayload` 发回 owner（JSON 含 `task_id/state/result/at`）；client：`ServerToolTransport.deliver()` 把 `mcp-*` 结果存入有界 `ExternalTaskResults`；`NumenActuator.taskResult` 读取；MCP 增加 `task_result` 工具 | 150–220 | N3（结构化终态） |
| P-02 external cancel | `.../api/NumenActuator.java`、`.../mcp/server/McpServer.java` | 增加 `cancel(companion)`：直接发 `CancelTasksPayload`（不依赖 `EntityAgentLoop` 是否存在）；MCP 增加 `cancel_companion` | 40–60 | N4（硬停止） |
| P-03 MCP chat tools（备选） | `.../mcp/server/McpServer.java` | 增加 `read_chat` / `send_chat`；不采用，聊天由 bridge 负责 | 50–100 | 不计划 |
| P-04 面板输入转外部（可选） | `.../client/screen/NumenScreen.java` | 面板 `onSend` 转 bridge；不采用，面板禁用即可 | 30–80 | 不计划 |

补丁管理：

- 基线固定：core `62e42d2`，numen-api `593c4d9`。
- 补丁文件放 `patches/numen/P-01-external-task-result.patch`、`P-02-external-cancel.patch`。
- 构建在 `vendor/numen-1.20.1/`（gitignored）或独立 fork 中进行；`refs/minecraft-numen` 保持只读参考。
- 记录 patched jar 的 SHA-256；升级/替换 jar 时重新验证。
- 不把补丁伪装成上游行为；文档和日志标明 `p15-patched`。

**P-01 的终态语义**：external task 的 `SUCCESS/TIMEOUT/CANCELLED` 映射为 `done/timeout/stopped`；`FAILED` 为 `failed`；记录 `taskId/verb/state/message/at`。同一 `taskId` 只保留第一个终态。结果 map 有界（如 64 条 / 10 分钟）；MCP `task_result` 对过期/未知 taskId 返回 `not-found`。

P-01 不能只在服务端记 map：MCP 跑在客户端，终态必须经 `TaskResultPayload` 发回 owner 客户端；`ServerToolTransport.deliver()` 对 `mcp-*` 结果额外写入 client-side `ExternalTaskResults`，`NumenActuator.taskResult` 才能查到。否则“task_stop 后知道失败/超时”仍然做不到。

**P-02 的停止语义**：`cancel(companion)` 要同时做到两件事——身体停手（`CancelTasksPayload` / `EntityAgentLoop.abort()` 的服务端链路）和调用方收到终态。external-only 场景下 `AgentLoopRegistry` 可能没有 loop（`NumenActuator.invoke` 不创建 `EntityAgentLoop`），因此 P-02 必须直接发 `CancelTasksPayload` 或等价的 client→server 取消，不能只依赖 `abort()`。若只发取消，external `NumenActuator.invoke` 的 `CompletableFuture` 可能仍在等待；需要在 `NumenActuator` 记录 in-flight 调用并在 cancel 时以 `cancelled` 完成，或由 Node 侧超时兜底。验收必须分别确认“身体停手”和“调用方收到终态”。

### 6.4 ChatBridge HTTP 契约

```text
GET  /health
  -> {ok, mod:"numen_bridge", version, mc, forge, sessionId, world:{worldKey, worldSessionId, dimension}}

GET  /chat?sinceSeq=<n>&n=<count>
  -> {ok, sessionId, lines:[{seq, at, text}], nextSeq}
  说明：seq 单调递增；text 为渲染后字符串（保留 § 码由 Node 清理）；最多 200 行。
        Node 检测 sessionId 变化时重置 sinceSeq（bridge 重启后 seq 从 0 开始），并记录一次 warn。

POST /chat
  body: {"text":"...", "mode":"local"|"bubble"}
  -> {ok, sent:true, seq, mode}
  限制：text <= 512 字符；去掉控制字符；默认拒绝以 "/" 开头（allowCommands=false）；
        mode=bubble 在 N1 可返回 not-implemented。
  本地输出格式：`companion名: 正文`（不添加玩家聊天装饰，避免被误认为真人 player chat）。

GET  /world
  -> {ok, worldKey, worldSessionId, dimension, server:"sp:..."|"mp:host:port"}

POST /stop
  -> {ok, requested:true, confirmed:false|true}
  说明：N1 调 MCP task_stop；P-02 后调 NumenActuator.cancel。
```

安全：

- 只绑 `127.0.0.1`；`token` 非空时要求 `Authorization: Bearer <token>`。
- 不把 token、世界种子、玩家 IP 写进日志/事件。
- `POST /chat` 不做权限提升；companion 只能以玩家可见文本发言，不能执行命令。
- 不接受外部任意 URL/文件路径。

## 7. 实施步骤

实施顺序固定为：N0 环境 → bridge 最小端点（`/health`、`/chat`、`/world`）→ Node MCP/bridge client → `NumenBody`/`factory`/`config` → 离线测试 → N2 语言脑 → N3 动作脑 → N4 加固。不要先写动作映射再补 bridge，否则 Node 会依赖不存在的端点，调试时分不清是 Numen、MCP 还是 bridge 的问题。

### 7.1 N0：环境与能力 smoke（2–3 天）

**任务**

1. 在测试实例安装 Forge 1.20.1-47.4.10 + Numen 0.1.1 + numen-api 0.0.8；记录 jar SHA。
2. 开启 `config/numen/mcp_server.json`，重启客户端；日志出现 MCP 端点。
3. 召唤 companion；用 MCP 依次调用：
   - `list_companions`
   - `get_self_status`
   - `get_world_info`
   - `scan_blocks {radius:16, block_ids:["minecraft:stone"]}`
   - `goto {x,y,z}` 或 `goto {block:"minecraft:crafting_table"}`
   - `mine {block_ids:["minecraft:dirt"], count:2}`
   - `task_status`（轮询）
   - `task_stop`
4. 记录每一步的耗时、返回 JSON、错误、身体是否真的移动/获得物品。
5. 测试 owner 离线/关客户端：确认 MCP 消失、companion 不保 chunk、任务不继续（作为非目标证据）。

**命令**

```powershell
node scripts/numen-live-probe.js --companion <name> --out runtime/evidence/p1.5/n0
```

**出口**

- `get_self_status`/`scan_blocks` 返回可用 JSON。

- 记录所有失败模式；若 MCP 不存在或 companion 无法运行，N0 失败，停止 P1.5。

   - `factory.js` / `config.js` / `index.js` 接线（`index.js` 增加独立 `numen` 启动分支，不能复用 `clientmod` 分支）；
   - `body.js` 增加 `readChat/clearChat` 默认。
6. 离线测试：fake MCP + fake bridge；覆盖 connect/chat/readChat/snapshot/action/stop/timeout/busy。至少包含：
   - MCP 初始化失败、bridge 不可达、companion 不存在/多个；
   - `readChat` 游标推进、bridge `sessionId` 变化重置、重复 seq 去重；
   - 异步任务 `task_id` → `running` → idle；`body-busy` 拒绝；`task_stop`；MCP 超时；
   - `chat` 拒绝 `/`、超长截断/拒绝、token 错误。
7. 真机：`body.kind=numen` 启动；`!status`、`@Agent hello`、`!mine dirt 2`。

**出口**

- N1-01…N1-07 全过。
- `npm run p1.5:test` 离线通过。
- 语言脑在 Numen body 下能收发聊天；不依赖 Numen 面板。
- `clientmod` 默认路径无回归：`p1:verify --fast` 19/19。

### 7.3 N2：语言脑接入（3–5 天）

**任务**

1. 确认 `ChatListener` 在 `body.kind=numen` 下启动（轮询 `readChat`）。
2. 聊天入口：vanilla chat 的 `@name`/`!`/普通聊天；复用现有解析与去重。
3. 聊天出口：`mc_say`/`reply.js` → `body.chat` → bridge；限制长度、防连发、防回声。
4. `mc_ask_player`：问题发出、`!answer` 收回、超时不是同意。
5. 关闭 Numen 内置大脑：确认 `McpMode.enabled()`；日志中 Numen LLM 请求为 0；面板输入锁定。
6. 人设/记忆：沿用现有语言脑；不读取/迁移 Numen 的 `config/numen/conversations`。

**出口**

- N2-01…N2-05 全过。
- 语言脑只通过 body 层收发聊天；Node 不直接读 Minecraft 日志/文件。
- Numen 内置 LLM 不产生 token 消耗。

### 7.4 N3：动作脑接入（7–10 天）

**任务**

1. 15 工具映射（§6.2）；不支持的返回显式 `unsupported-body`。
2. `NumenTaskTracker` 终态：N1 轮询 + 观测；打 P-01 后读 `task_result`。
3. 计划/任务：`mc_plan` 的步骤映射到 Numen 工具；`mc_cancel` 先失效资格再 `task_stop`/P-02。PlanRunner 需要按 body capability 选择步骤执行器：不支持的原语在计划期拒绝，不能执行到一半才报 `unsupported-body`。
4. 失败阶梯：把 Numen 的 `success:false/message` 映射到现有 failure class；无 input-layer 回退。
5. 忙时拒绝：第二个身体动作返回 `body-busy` + 当前 taskId；不排队、不替换。
6. 代表任务：
   - `!mine dirt 2`（或 `mc_step mine dirt 2`）；
   - `goto` + `interact_at`（使用工作台/容器）；
   - `craft` 一件物品；
   - 失败路径：不可达坐标 / 无工具挖矿。
7. 打 P-01；重新跑终态用例。

**出口**

- N3-01…N3-06 全过。
- 至少 3 类动作闭环；失败有结构化原因；忙时拒绝；无静默成功。
- 不改 P2 runtime；P2 合同扩展另开任务。

### 7.5 N4：真机加固与验收（7–10 天）

**任务**

1. 死亡/复活：companion 死亡 → 任务取消、无后续动作；复活后重新感知再派任务。
2. 断线/重连：`worldSessionId` 变化；旧 task/结果被拒；不重放。
3. 换世界：单机存档 A→B；`worldKey` 变化；只记录，不混账本（分区属 P2）。
4. 硬停止：运行中 `stop`；P-02 后 1s 内停手；无新动作；确认状态。
5. 性能：chat 往返、observe、action accepted、终态检测的 p50/p95；与 clientmod 同场景对比（只比延迟，不比工具语义）。
6. 回归：`p1:verify --fast` 19/19、`action-brain:contract:test` 63/63、`docs:check` 14/14。
7. 写验收报告与残余风险。

**出口**

- N4-01…N4-07 全过，或明确 BLOCKED 并写原因。
- 未过项不得用“默认已支持”表述；默认仍是 `clientmod`。

## 8. 验收标准

级别：F = 离线夹具；G = 真机；W = 文档/交付。证据目录 `runtime/evidence/p1.5/<batch>/`。

每批证据至少包含：

- `manifest.json`：git HEAD/`git status` 摘要、Numen/numen-api jar SHA-256、MC/Forge 版本、companion 名、存档/服务器标识、脱敏配置、实际执行的用例顺序；
- `cases.jsonl`：caseId、level、status（PASS/FAIL/BLOCKED/PARTIAL）、expected、actual、evidence 引用、blocker；
- `events.jsonl`：MCP 请求/响应、bridge 请求/响应、taskId、时间戳；不存在的字段写 `null`，不伪造；
- 原始聊天记录、任务状态轮询序列、身体动作前后观测（位置/背包/方块）。截图在 Numen body 下写 `null`。

## 9. 风险、回退与 Kill criteria

### 9.1 风险

| 风险 | 触发 | 影响 | 缓解 |
| --- | --- | --- | --- |
| owner 客户端离线 | 关客户端/退服 | MCP 消失、任务停、复活不发生 | 文档写明；启动时检查 `/health`；不假装 ready |
| 1.20.1 冻结 | 上游只维护 1.21.1 | 无修复；补丁需自维护 | 固定版本/jar SHA；补丁最小化；不追新 |
| 外部任务无终态 | 未打 P-01 | 只能轮询+观测，终态可能误判 | N1 只用观测；N3 前打 P-01；证据标注 |
| 硬停止不足 | 未打 P-02 | 同步动作停不住 | N4 前打 P-02；否则 N4-04 FAIL |
| 聊天只有 owner 可见 | 默认 `ChatLines`/本地聊天 | 其他玩家看不到 | N1 明示；全服广播另立任务 |
| 工具语义不匹配 | `mine`/`build` 与现有技能差异 | 技能失败/误判 | 只保支持子集；不支持显式失败；逐步重写技能 |
| 截图/输入层失效 | 无客户端相机/键鼠 | M5 证据/视觉任务不可用 | 非目标；文档标注；不转填 P1 通过 |
| LGPL/ARR | 打包/修改 Numen | 分发风险 | 用户自装；bridge 不 import 内部类；补丁按 LGPL |
| 双身体/双大脑 | Numen 生存反射 + 我们的任务 | 抢占/停止不确认 | 只走 Numen 任务闸门；N4 停止测试；保留反射可见性 |
| 端口冲突 | 8765/8898 被占 | 启动失败 | 配置可改；启动时明确报错 |

### 9.2 回退

1. `body.kind` 默认仍 `clientmod`；P1.5 只通过 `--body numen` 或 `config/agent.local.json` 启用。
2. 失败时删除/停用 `numen` 配置即可回退；不需要迁移运行状态。
3. Numen 补丁只作用于 `vendor/numen-1.20.1`；原始 jar/客户端不受影响。
4. bridge mod 可单独卸载；不影响 clientmod。
5. 证据与日志分开存放，避免污染 P1/P2 账本。

### 9.3 Kill criteria

满足任一即停止 P1.5 或降级为只读 spike：

1. N0 无法在 1.20.1 Forge + 当前客户端稳定运行 Numen。
2. N1 无法在不 fork 的前提下完成聊天读写和基本动作。
3. N1 的停止在 2s 内无法确认，且 P-02 补丁成本不可接受。
4. N3 的 15 工具映射需要重写大部分技能且无法在 2 周内闭环。
5. N4 的可靠性/延迟明显差于 clientmod，且无明确收益。
6. 许可/分发模型无法接受（用户自装也解决不了）。
7. 产品必须无客户端/纯专服（当前架构不支持，需另立项目）。

## 10. 工作量与排期

粗估（1 名熟悉 Forge + Node 的工程师；不含等待用户装环境）：

| 阶段 | 内容 | 估算 |
| --- | --- | --- |
| N0 | 环境、MCP 探针、失败模式 | 2–3 天 |
| N1 | bridge mod + NumenBody + 离线测试 | 7–10 天 |
| N2 | 语言脑聊天/提问/禁用内置脑 | 3–5 天 |
| N3 | 15 工具映射 + 计划/失败/忙拒 + P-01 | 7–10 天 |
| N4 | 死亡/断线/换世界/硬停/性能/回归 | 7–10 天 |
| 补丁 | P-01 + P-02 应用与验证 | 2–3 天 |
| 合计 | 单机/自建服 + 有客户端 | **5–7 周** |

- 两人并行（Java bridge + Node）可压到 3–5 周，但 N0/N4 必须同一人负责真机。
- 无客户端专服另加 4–8 周并承担 fork 维护；不在本计划。
- 以上是工程估算，不是上线承诺；N0 后按实际失败模式重估。
