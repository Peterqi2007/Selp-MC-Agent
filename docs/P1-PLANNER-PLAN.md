## 一、架构设计方案

### 1.1 已确认边界与实施建议

以下边界来自本轮讨论，作为重构约束：

1. 语言脑与动作脑分别调用 LLM。语言脑不调用身体、技能或任务工具；动作脑负责理解任务、检查能力、规划、学习与执行。
2. **`!` 指令无条件通过语言准入，不调用 LLM 审查。**其他需要准入审查的指令或玩家回答，语言模型只能放行或不放行，不能改写原文再交给动作脑。
3. 无法生成计划时，应补充学习并向玩家具体询问如何处理，保留任务以便继续，不直接以“干不了”结束。
4. 感知采集与 LLM 调用分离。动物、掉落物和任务目标的详细追踪由相关任务按需执行；保留原有保命反射所需的数据。
5. 技能不是状态，不进入状态记忆池。当前只有一个服务器，不建设多服务器管理与迁移架构。
6. 自动写代码是需要实施的高级能力。新技能与原有技能分目录管理，在 agent 下线检修时完成测试和正式晋升。
7. computer_use 必须具备执行期间的实时反馈。普通聊天是否适合插话由模型根据上下文判断，不以关键词匹配作为调用模型的硬门槛。
8. 常规采矿继续由确定性代码完成，LLM 块级操作只处理异常恢复，不推广为全部挖矿的预先完整行动计划。

下文的接口字段、预算默认值、技能试运行机制、验收样本量等属于**建议实施细节**。可按实际测量细化，但调整应记录原因，并保持上述边界。

### 1.2 整体分工与信息流

```text
游戏聊天 / 控制面板
        |
        +-- !指令 ------------------------------+
        |     原文保留、免语言审查                |
        +-- @自然语言 / 玩家回答 --> 语言准入闸门 -+--> 请求记录 --> 动作脑
        |                         仅放行/不放行              |
        +-- 普通聊天 --> 语言脑：回复或沉默                    |
                                                            v
                         定向感知 / 方法检索 / 联网学习 / 向玩家求助
                                                            |
                                                            v
                         计划与步骤 --> 统一执行器 --> 技能 / body / computer_use
                              ^             |                          |
                              +--- 验证、结果、异常与新观察 <-----------+
                                             |
                                    经验与候选技能沉淀
                                             |
                                 语言脑依据事实生成播报

保命反射：独立于 LLM 调用运行，经统一执行权机制中断或暂停普通任务。
```

职责可以分成六类：Planner 选择下一步，Critic 检查计划约束，Executor 执行，Verifier 检查真实结果，State 提供观察，Replanner 修订未完成部分。**这是职责分解，不要求部署六个 agent，也不要求每步调用六次模型。**参数、资源、执行与可直接计算的结果验证优先由代码完成。

### 1.3 双脑契约、消息路由与人格

#### 1.3.1 准入闸门只决定放行

请求信封建议至少包含：

```js
{
  requestId, messageId, source, actor, receivedAt,
  kind,                    // command | natural_task | answer
  rawText,                 // 接收时封存，审查模型无权替换
  replyToRequestId: null,   // 玩家回答与等待中的任务关联
  gate: { mode, decision, reasonCode }
}
```

- `!`：直接记录 `gate.mode=bypass`、`decision=allow`，进入确定性命令解析。人格、模型不可用或审查超时不能阻挡该路径。
- `@` 自然语言任务及任务求助中的玩家回答：审查输出只允许 `{ decision: 'allow' | 'reject', reasonCode }`。拒绝时可以生成解释，但不能附带一个“修改后的任务”派发。
- 放行后由动作脑把原文解释成结构化目标；目标、数量、对象和约束必须可追溯到原文。歧义交给玩家澄清，不静默替换任务。
- 审查格式错误或模型不可用时，不把消息自动变成动作；保留请求并说明等待或重试。`!` 路径仍可使用。
- 已提交审查的文本按原文放行或拒绝；语言脑生成任务播报、普通回复是独立职责，不意味着准入闸门可以改写玩家输入。
- 未实现命令、非法参数、目标不存在、材料不足等由执行侧返回具体结果；这是能力或前置条件检查，不是人格审查。放行不等于保证成功。
- 语言准入与对话上下文不注册身体工具入口，不能仅靠提示词禁止调用。

**语言脑的工具面（2026-10-17 定，Q3）**：语言脑**不持有**任何 body / 技能 / 任务 / 主动感知工具，只保留三类能力：① 读取 Node 采集好的状态摘要（`ctx.memory` 与持久化 state，**注入上下文**，不是让语言脑主动调用 `observe`）；② 检索/搜索（方法知识与联网资料）；③ `say` / `silence` 输出。执行入口全部在动作脑。

- 工具面收窄的执行点是 `src/llm/blackboard.js:212-260` 的 `systemPrompt` 工具段与 `src/llm/tools/registry.js` 的注册表拆分，**不是提示词自觉**；A03 按此断言。
- 普通闲聊不由状态感知事件触发，因此语言脑不需要主动感知工具；状态摘要随上下文注入即可。
- `!` 免审查与"未受请求回合不得派活"（`LlmCore.actionDropped`）保持不变。

#### 1.3.2 `!shoot player` 与 persona 同步

原文“违背人格底线，所以不存储任务记录”调整为：**保留事实执行记录，区分执行事实与人格倾向学习。**记录原始指令、发起者、`!` 免审查来源、目标和结果；不能因一次受命射击，自动学成“喜欢攻击玩家”或自主攻击规则。

这部分涉及 [`persona.md`](../config/persona.md) 调整：需要明确受命行为如何成为角色经历、哪些内容不转化为自主偏好。若希望角色不主动回忆某类经历，应在角色记忆检索层区分，不能删除诊断所需的执行事实。

persona 还需同步清理以下冲突：

- “没被叫到就不出声”与允许合适插话冲突；“不做没被要求的事”应区分自主提案与未经接受就执行。
- 写死“不能合成”等能力结论会过期；能力事实改由技能注册表和当前前置条件提供。语言脑区只进行底线审查，不再负责能力审查。
- 语言模型同时输出 `say/action` 并派任务的旧示例，与职责隔离冲突；改成准入、对话和动作脑各自的示例。

本条是代码实施阶段的关联交付要求，本次仅修改 P1 文档。

### 1.4 统一任务契约、执行权与恢复状态

先统一执行基础，再增加自主能力。不能让旧 Brain 队列、TaskHub、规划器和 computer_use 同时控制同一身体。

#### 1.4.1 身份与结果

使用可跨重启区分的身份链：`requestId → planId → stepId → taskId`，执行尝试附 `attemptId`。自主提案被接受后也建立请求；反射使用独立来源与事件 ID，不冒认玩家请求。

| 对象 | 最少信息 | 必须解决的问题 |
| --- | --- | --- |
| Capability | 技能名、参数 Schema、版本、静态支持、当前前置条件、可验证后置条件 | 区分“不支持”和“暂缺材料”；不同入口不再各写能力判断 |
| Plan | 原始目标、约束、步骤依赖、完成条件、版本、学习/执行预算 | 可追溯原文，修订只影响未完成步骤 |
| Step | 输入、预期结果、依赖、所需执行权、重试策略 | 不只靠自然语言描述判断完成 |
| Progress | 阶段、可比较计数/距离、目标身份、最近有效进展时间 | 不以对象引用是否相等判断停滞；有效进展须有证据 |
| TaskResult | 状态、原因、证据、实际增量、未完成部分、可恢复信息 | accepted、函数返回和动作发送成功不等于目标完成 |

结果状态建议至少区分 `succeeded / partial / blocked / failed / cancelled / unknown`。适配层保留原始结果，不能把 partial 或未收集产物压缩成无条件 `ok:true`。

完成事件按身份准确匹配请求，重复事件幂等消费。过期计划的模型结果、已取消任务的回调和乱序事件必须可识别；禁止以“第一个未关闭请求”猜测归属。

#### 1.4.2 唯一身体执行权

1. 统一执行器仲裁身体操作，保留紧急反射高于显式任务、显式任务高于自主活动的优先级。聊天与只读检索不取得身体执行权。
2. 父计划保存逻辑状态；子步骤走内部执行接口，不能每步再次外部 `TaskHub.submit`，把父任务当作旧任务替换。复用或迁移已有取消、等待停止与结算机制。
3. 反射抢占时先中止导航、持续动作与按键，确认停止后再操作。普通任务进入可诊断的暂停/中断状态，恢复前重新感知、校验。
4. 旧执行者未确认停止时不启动另一个执行者。超时保留占用并报告阻塞，不能只清空标志继续动作。
5. 停止、死亡、断线和人工接管使后续模型输出失效。死亡后不自动恢复；普通暂停仅在恢复条件满足时继续。

#### 1.4.3 任务闭环

```text
接收目标 → 定向观察与能力检查 → 检索方法 / 补充学习 → 生成计划
                                  |                     |
                         信息仍不足：向玩家求助          v
                                  |               执行一个步骤
                                  v                     |
                           waiting_for_player           v
                                  |              验证目标与实际状态
                     回答原文准入、关联、更新方法          |
                                  +--> 修订未完成计划 <---+-- 异常 / 条件变化
                                                        |
                                                 达成目标、沉淀经验
```

规划状态至少覆盖 `observing / learning / planning / executing / verifying / waiting_for_player / paused / terminal`；`waiting_for_player` 不是失败终态。

- 优先选择能完成目标的现有技能；复杂目标只拆到执行能力能承接的粒度。独立只读操作可以并发，身体动作串行仲裁。
- 缺知识进入检索或搜索，缺方法进入讨论或代码技能生成，缺物资则规划获取或询问玩家；不能都归成“不支持”。
- 无法生成计划时，说明缺少的规则、方法或条件，提出具体问题，保留已完成步骤。问题发出前落盘，回答附 `replyToRequestId`；多个待答任务且归属不明时先澄清。
- 明确的环境约束也应说明并询问替代路径，例如权限不足时询问更换地点或请玩家协助。玩家取消后按取消结算；预算耗尽不证明任务不可完成。
- 等待玩家期间保命反射继续；释放身体前清理持续动作。没有新回答/事件时，不重复调用模型生成同一问题。
- 步骤完成、前置条件变化、失败、有效进展停止、收到指导时触发计划修订。定时采集没有新信息时不唤醒规划 LLM。
- 搜索、重规划、重试、模型请求与总时长分别有有限预算。初始建议每轮最多 3 次外部检索、2 次同因重规划，之后求助；新信息到来后建立新一轮预算，保留累计消耗。数值不是实测结论，M0/M3 记录后调整。

#### 1.4.4 事件汇聚、计划版本与 SSE 投递

**唯一事件汇聚点 `taskEvents`。** 现在有两处发射：`brain.js:702/:712`（`task:done` / `task:failed`）与 `taskHub.js:273`（同一组事件给 LLM 与主动发言消费）。两处各自投递正是"同一件事播两遍"的根因之一。改为：两个 emitter 只写入 `taskEvents`（统一字段 + 身份链 `requestId→planId→stepId→taskId→attemptId` + 去重 + 持久化），SSE、面板与账本**只订阅 `taskEvents`**，不再各自订阅两个 emitter。

**传输：同端口，不另起 8767。** 在 `statusServer` 的同一 server 上增加 `GET /events`（SSE）。理由：`statusServer.js:288-303` 已在 8766 被占用时 fallback 到 `port + 1`，另开 8767 会与之撞车，还会带来双监听、端口协商与两套鉴权。

**鉴权**：`EventSource` 不能发送 `Authorization` 头。首选 **`fetch` + `ReadableStream` 读流**（可带 Bearer，复用现有 token）；退化方案是 query token + 服务端只接受本机来源。两种都不允许把 token 写进日志。

**断线重放**：事件序号单调递增，客户端带 `Last-Event-ID` 重连；服务端按持久化事件回放，保证**不丢、不重**。传输层保活与"模型查状态"是两件事，保活不计模型调用。

**计划版本单一写者**：harness 只提交"步骤草案"，Node 校验后落盘为权威计划并 `planVersion++`；重规划只改未完成步骤。**禁止两进程同时写计划**——那会互相覆盖且无法归因。

### 1.5 感知：按用途采集、按事件调用模型

#### 1.5.1 当前证据边界

[`clientModBody.js`](../src/body/clientModBody.js) 存在默认 `statePollMs=500` 的后台轮询实现。**用户未测试该 500ms 后台轮询，未有对应实测验收记录。**不能据此宣称数据必然保持在 500ms 内、反射及时或性能已合格；请求失败仍可能继续返回旧缓存。

当前 [`ClientStateSnapshot.java`](../mod-client/src/main/java/dev/agentclient/ClientStateSnapshot.java) 的 `/state` 合并生成背包、农田、方块、敌对实体、掉落物等内容。减少 LLM 读取或 Node 消费缓存的次数，不自动减少 Mod 世界扫描；需在采集边界优化，先测不同字段成本。

现有反射已经读取生命值、环境危险与附近敌对实体，不能把现状概括为“无任务就完全不感知”。P1 新增的是规划可使用的按需观察、数据新鲜度与分层采集。

#### 1.5.2 用途与采集策略

| 类别 | 信息 | 建议采集方式 | LLM 调用 |
| --- | --- | --- | --- |
| 生存与保命 | 生命、饱食、氧气、燃烧、异常效果、脚下危险 | Mod 事件或轻量读取，满足现有反射需要；周期经真机测量确定 | 反射直接运行，不为每次采集请求模型 |
| 最低限度威胁 | 受伤、近距敌对实体进入/离开威胁范围 | 保留反射最小观测，可用事件配合补偿检查；不做全实体长期跟踪 | 默认只供反射；任务被中断等语义变化再通知规划器 |
| 自身与物资 | 坐标、维度、时间、天气、快捷栏、护甲、库存 | 事件更新缓存；任务开始、阶段变化和验证时按字段刷新 | 需要决策/回答时读取相关摘要 |
| 任务实体 | 动物、战斗目标、掉落物、其他玩家位置 | 相关任务、明确询问或定向探索时启用，结束即停订阅 | 任务代码详细追踪，模型接收必要结果与异常 |
| 工作区与特殊方块 | 容器、床、门、工作台、模组设备、水/岩浆、农田 | 按任务所需范围与类型请求；位置/区块变化时失效 | 只提交当前目标所需观察 |
| 地形与环境知识 | 生物群系、落差、水域、地貌 | 定向探索、导航或新区域需求触发，不做全图定时扫描 | 用于明确的探索/规划问题 |

箱子等容器按方块/方块实体与界面信息处理，不混入动物类移动实体追踪。

不为动物、怪物、掉落物建立 500ms–3s 的通用自主扫描并持续灌入规划上下文。最低限度威胁观测属于保命反射的数据依赖，与任务实体详细追踪分开，不要求空闲规划器持续理解怪物动向。

#### 1.5.3 观察契约与缓存

提供任务代码与动作脑工具可共同使用的 `observe({ fields, area, maxAgeMs, purpose })` 类接口。名称待实现时确定，契约需满足：

- 记录 `observedAt`、`revision`、维度、范围、来源与有效性；不同时间采到的字段不能伪装成同一时刻的原子快照。
- 超过消费者要求的新鲜度时刷新；失败返回 stale/unknown 与最后成功时间，不把旧缓存标成当前事实。安全关键动作在信息不足时暂停或走已有保守分支。
- 同字段同范围的并发请求合并；缓存可由任务与反射共享，不强制维护两套相互矛盾的事实。
- 下层可拆字段接口、按需订阅或使用不同缓存周期，以实测选择；避免上层分层、底层仍每次全扫。
- 初始化只采必要自身状态；任务实体和大范围地形按需加载。优先级不机械等同于固定轮询周期。
- 任务内部保留低层观测与确定性控制，向规划器提交阶段、进展、完成和异常，不提交每个移动 tick。

状态缓存按字段设有效期，在维度变化、断线、死亡等情况下及时失效。游戏三天可作为部分环境摘要的最长保留建议，不能保证移动实体位置有效；技能、方法知识和执行记录不适用状态遗忘规则。

**实施顺序（2026-10-17 定，Q7）**：M0 先测各字段族的采集成本，M1 过渡实现为"**Node 侧逐字段打时间戳 + 按需 `refresh`**"，不先拆 Mod 端点；字段成本表出来后再决定是否拆分 `/state`。**A09 的判定口径**：空闲期间"模型调用为 0 + 无新增订阅"，**快照刷新本身不算违规**（否则现实现的 500ms 轮询永远过不了这条）。

### 1.6 记忆、联网学习与玩家指导

#### 1.6.1 分类存储

| 存储 | 内容 | 更新与检索 |
| --- | --- | --- |
| 状态缓存 | 当前自身、库存、局部环境观察 | 按新鲜度读取和失效，不作为永久真相 |
| 对话记忆 | 原始消息、对象、时间、任务关联、滚动摘要 | 持久化日志、摘要及按需检索，保留原文索引 |
| 任务执行记录 | 身份链、步骤、结果、证据、失败原因、资源与调用消耗 | 结构化事件索引，必要时用 `rg` 检索原始日志 |
| 方法知识 | 配方、机制、任务拆解、玩家纠正、适用条件、来源 | 检索相关方法，使用前检查适用条件 |
| 技能库 | 程序、参数/结果契约、版本、依赖、验证与晋升状态 | 注册表查询；不混入短期状态缓存 |

关键词检索是第一版可用方案，但需 item ID、模组名、技能名等稳定字段和常用别名索引；不能只靠自然语言日志恰巧出现同一个词。暂不要求建设向量数据库。

不能因模型支持大上下文就每次全量注入对话。保留近期对话、当前目标、未答问题和相关检索结果，为各类内容分配 token 预算；超预算时压缩旧内容，原文仍可追溯。

#### 1.6.2 两个学习入口

1. **规划前补知识**：检索已有方法与技能，不足时联网搜索；仍有缺口就向玩家提问，保存回答原文、适用条件与任务关联，继续原目标。
2. **执行后更新方法**：实际结果与预期对照，保存成功条件和失败原因，修订未完成计划；重复方法形成候选技能。模型总结不算成功证据。

联网搜索作为正常学习渠道，优先 MC 百科、模组文档和对应版本资料，必要时用搜索定位内容，不把单一站点硬编码为唯一来源。保留 URL、检索时间、版本/模组与关键结论，不要求每条知识重复人工核验。

“资料基本可靠”与“当前环境可执行”分别处理：自动检查当前配方、材料、设备、权限和状态；资料与实测不符时更新方法知识，必要时询问玩家。网页、历史日志和检索文档是资料，不具有修改玩家目标、persona、执行权限或运行配置的指令权。

学习需记录方法适用条件，如模组版本、工具、工作台类型与空间条件。玩家方法可立即用于推理；未经运行验证时标记“玩家提供、待执行验证”，不伪造成功。

### 1.7 自动编写与注册代码技能

自动写代码是高级阶段的正式交付，不能无限期延后。适用于稳定重复操作、现有技能缺失、复杂 GUI 流程，以及 computer_use 反复试探成本过高的任务；已有技能可完成时先复用。

#### 1.7.1 目录与生命周期

保留 `src/skills/` 作为原有技能目录。建议新增 `agent-data/skills/candidates/` 与 `agent-data/skills/promoted/`，实施时核对配置、版本管理与忽略规则，不要求迁移全部现有技能。

建议生命周期为 `candidate → trial → awaiting_review → promoted`，另设 quarantined 标记失败/禁用版本：

1. 在线生成程序、manifest 和方法说明，保存到候选目录；检查参数、输出、依赖与执行接口。
2. 为解决当前任务，走显式的**试运行路径**调用指定候选版本，普通技能检索不默认选中它。试运行不是正式晋升，不增加每次必须询问玩家批准的流程。
3. 试运行复用统一执行器，限制时长、动作、模型/搜索预算；验证环境效果并记录版本。失败版本停用，不无限原样重试。
4. agent 下线检修时重放日志，做离线与适用场景测试，检查取消、清理、边界输入和原有能力回归；通过后写晋升记录。
5. 发布到晋升目录，登记名称、版本与契约；正常检索默认只返回内置和已晋升技能，保留上一版本供回退。

若候选技能没有可取消、可验证的试运行接口，先保存待检修并向玩家说明当前缺口。不能让“下线后才能测试”成为全部在线学习无法落地的障碍，也不能把尚未运行的代码当作已掌握能力。

#### 1.7.2 执行边界与成功条件

- manifest 至少声明名称、版本、输入 Schema、依赖、前后置条件、预算、允许调用的能力、清理方式、验证状态和日志位置。
- 候选不得覆盖内置技能、修改 persona/任务原文或绕过身体执行权；同名冲突使用独立命名空间与明确版本。
- **分目录不等于运行隔离。**候选不能直接以主进程权限任意 `require` 后执行。建议受限运行器通过代理能力接口请求游戏动作，只给所需工作目录，不提供宿主凭据与任意系统操作能力。
- 独立进程也不构成完整沙箱；若运行器不满足文件、网络与宿主访问边界，应先补边界或使用受限程序表示，不能把约定当成技术保证。
- 运行器失联、超时、异常退出时，宿主撤销执行权、停止动作，保留 unknown 等真实状态；按键释放与取消不能只依赖候选代码自行清理。
- 网页知识可用于生成代码，但不直接执行网页命令。可编译、静态检查通过与真实目标达成是三个阶段，最终成功由后置条件验证。

#### 1.7.3 动作脑后端的工具面（与候选技能隔离并列的边界）

动作脑若由 DSH 承载，**它自己的工具面就是一条比 `permissionGate` 宽得多的边界**：`standard` preset 默认带 `tool-bash`/`tool-pwsh`、`tool-fs`、`tool-fs-search`、`tool-web`。P1 为动作脑单开一个 preset（不改 `standard`）：

| 能力 | 设定 | 理由 |
| --- | --- | --- |
| bash / pwsh | **关闭** | 候选代码必须走 M4 的受限运行器，不给宿主 shell |
| fs | **只读工作区 + 只写 `agent-data/`**（候选、账本、记忆） | 与生态项目的 MC 模式边界同思路 |
| web | **只经 Node 的检索代理** | 便于记录 URL/时间/版本，且不把网络出口交给动作脑 |
| 游戏动作 | **全部来自 Node 的 `executeStep`** | 唯一身体执行权不因接入 harness 而破 |

这条边界未就绪时，M4（生成代码）与 M5（CU）都不得开放。

### 1.8 computer_use：特殊场景的观察—动作闭环

用于现有语义技能/接口不能覆盖的场景，如特殊模组 GUI，不作为所有复杂问题的无限重试路径；稳定操作应逐步提炼为技能。

#### 1.8.1 观察与控制

- 进入前取得身体执行权，确认窗口、界面 ID、焦点、分辨率/缩放、截图时间与结构化界面信息。优先使用可靠的槽位、物品和状态数据，截图补视觉语义。
- 每步“观察 → 少量动作 → 新观察 → 验证”。截图/状态附 `frameId`、`observedAt`、`revision` 与关联 `actionId`，不能用动作前截图当动作后证据。
- 动作完成、GUI 变化、错误、无进展时请求新决策；持续移动/长按需要本地中途监测，时长有上限。感知刷新不要求每次请求截图模型。
- 视角、移动、攻击、破坏、GUI 点击经统一身体接口，不另起无限制键鼠控制器。开关菜单、释放按键、中断有明确回执。
- 合成、转移和设备操作检查实际库存、槽位或设备状态；点击已发出或画面变化不单独证明成功。

#### 1.8.2 中断与复用

界面意外关闭、分辨率变化、失焦、反射、人工接管、死亡/断线时，停止动作批次、释放按键、使旧观察失效。恢复前重新定位界面并核对物品，不能继续点旧坐标。

代码追踪短期状态，LLM 在需要理解或决策时调用。成功流程形成带前置条件的语义脚本/候选技能，验证复用后减少重复截图推理。GUI 版本变化需重新验证，不把一次成功坐标序列推广为全部界面的通用方法。

#### 1.8.3 实现载体与可行性闸门（2026-10-17 定，Q5）

CU **复用现有 `dsh-computer-use` 插件**（本机 desktop profile 的 bundles 已含），不自行实现键鼠层；操作与截图范围**限制为游戏窗口**，并用提示词强化约束（窗口/界面/失焦判定、不做与任务无关的点击）。

**可行性闸门 F1（M0 先行）**：验证该插件能否把操作与截图范围限制到 Minecraft 窗口。**做不到就按裁决放弃 CU**——M5 的 A21/A22 标记 N/A 并写明原因，不允许用"提示词约定"代替技术限制。CU 放弃不影响 P1 其余交付。

### 1.9 第 6 点：coding harness 与自研动作脑的比较、接入和选型

**状态：接入设计已补、路线已定（先接 harness）；spike 与生产接入待执行，A/B 对照仅在 §1.9.2 判定成立时执行。**这里的 coding harness 指提供模型回合、工具执行、上下文管理与编码工作流的运行框架，不等同于某个模型，也不等同于只让模型返回一次计划 JSON。

#### 1.9.1 结论与适用范围

**针对完整 P1，优先验证并接入 coding harness，承担动作脑的规划、学习和代码生成；保留并重构 Node 的任务运行时、确定性技能、执行权和结果验证。**如果近期仅需要组合几个现有技能，自研轻量规划器可能更快。完整目标还包含联网学习、生成和修复技能、长任务恢复，继续自研就需要逐步承担这些通用 agent 设施的维护。

这不是“接框架即可完成 P1”。双脑路由、身体互斥、任务结果关联、入包验证、玩家回答恢复等工程仍由本项目交付。也不能把自研描述成完全从零开始：仓库已有模型客户端、工具注册表、有限回合和局部恢复循环。

| 比较项 | 接入 coding harness | 复用现有代码自研任务拆解 agent | 对本项目的判断 |
| --- | --- | --- | --- |
| 现有简单任务适配 | 需要宿主适配和工具包装，初始成本未必低 | 可直接接现有 LlmClient、工具和技能 | 只做已有技能组合时，自研有先发优势 |
| 完整规划与学习闭环 | 可复用多轮工具、会话及编码设施，但必须验证实际可用接口 | 自主掌握循环和状态，需补学习、重试、压缩及恢复 | 完整 P1 更值得先验证 harness |
| Forge 客户端适配 | 现成 Mineflayer 工具不能直接替代本项目的 Mod/body | 与当前 Node/body 契约贴合 | 两者都经本项目 Node，不能绕过执行器 |
| 自动生成技能 | 通常已有文件编辑、运行反馈和修复流程 | 需提供等价文件/测试工具与修复循环 | harness 的主要价值需用代码生成场景验证 |
| 生命周期和实时响应 | 依赖外部启动、续轮、取消和事件接口；宿主版本会影响适配 | 可直接控制事件和取消，但实现质量由自己承担 | 停止和反射必须在 Node 本地完成 |
| 上下文与长期状态 | 会话/压缩可复用，内部开销和行为需审计 | 可定制最小上下文，压缩/恢复策略需自己维护 | 长期任务事实以 Node 持久化记录为准 |
| 模型/供应商兼容 | 受框架工具协议、端点、认证和版本共同约束 | 可复用 OpenAI-compatible 客户端，仍需处理供应商差异 | 同一模型能否公平对照先做接口探针 |
| 扩展与维护 | 跟随上游能力，承担版本固定、升级回归和适配变更 | 完全可控，新增通用功能和修复长期由本项目承担 | 不预设哪方维护成本低，记录实际变更人时 |
| token、费用和时延 | 工具说明、内部回合可能增加开销，也可能减少修复重试 | 初始工具面可小，但循环质量差也会重复消耗 | 不预设 harness 更贵或自研更省，按全请求账本比较 |

自研方案不必建设多 agent、树搜索或六个模型角色；一个有预算、有工具、有事件恢复能力的动作脑即可作为有效候选。harness 也不要求把语言脑、反射和所有低层操作迁进去。

`HARNESS-INTERFACES.md` 保留当时取证。其涉及“不能做语言脑”“工具可见性只能由一个字段控制”等较宽推论，不提升为通用事实；本方案分离双脑是项目设计要求。某本机配置未启用某 provider，不等于该产品在其他版本没有该能力。官方网页抓取当时受限，未补到的最新版本/价格/稳定性保证均待执行实验前核实。

候选顺序建议：

1. **先验证 DSH**：在当前使用 DeepSeek 的条件下，已有 preset、插件、提示词装配和 Minecraft 生态资料，适合作为第一条适配路线。先固定版本并验证宿主双向接口，不直接修改日常桌面 profile。
2. **Codex 保留为候选**：程序入口已从本机帮助确认；模型端点、工具协议、续轮、取消、计费可见性仍需实测。更换候选意味着另开实验批次，不能与 DSH 样本混算。
3. **降级触发的判定口径（2026-10-17 定，四条）**：
   - **接口稳定性**：只认随包文档/公开扩展点；凡需未公开内部字段、UI 自动点击、或绑定单一版本的私有钩子 ⇒ 判"不稳定"。
   - **预算边界**：必须能在**发请求前**设上限，且请求后能拿到**可归属**的 usage；缺任一项 ⇒ 判"不能满足预算边界"。
   - **任一成立只触发** [`PLANNER-AB-EXPERIMENT.md`](PLANNER-AB-EXPERIMENT.md) §10 第 2 项（8 次配对运行），**不直接跳到 24 次**。
   - **spike 是闸门，24 次 A/B 是条件动作**；触发判定与证据记入 M0 的决策记录。

#### 1.9.3 接入方式：一个高层规划者，Node 执行与验证

同一任务只有一个高层规划者。选择 harness 后，Node 保存计划、检查前置条件、执行已授权步骤、验证后置条件和调度事件，不再运行另一套 LLM 高层规划器重拆同一目标。语言脑继续独立；采矿内部的局部恢复仅在已有 owner 下运行，父计划等待其结果，不同时下发另一条身体动作。

**需要双向通道。MCP/插件注册工具只解决其中一半，不保证宿主自动开启下一轮。**以下为拟实现的适配契约，名称不是现成 API 承诺：

| 方向 | 建议能力 | 约束 |
| --- | --- | --- |
| harness → Node | `observe`、`listCapabilities`、`executeStep`、`getTaskResult`、`askPlayer`、`stop` | 工具经插件/MCP 或等价桥接；执行前校验身份、版本、参数、执行权和预算 |
| Node → harness | `startTurn`、`resumeTurn`、`cancelTurn`、`closeSession`（**同端口**：`GET /events` SSE + `POST /turns`） | 经候选宿主公开 API/插件事件实现；**不得新开 8767**（`statusServer.js:288-303` 会占用 `port+1`）；传任务结果、前置变化、玩家回答等；不靠桌面 UI 自动点击 |
| Node → 持久化记录 | 请求、计划版本、步骤结果、问题、候选版本、事件消费位置与预算 | harness sessionId 是关联字段，不是唯一任务数据库 |
| 候选技能 → Node | 受限能力代理、指定版本试运行与结果回传 | 不能拿到完整 body/宿主凭据，不能绕过取消和身体执行权 |

建议运行流程：

1. 请求经既有路由进入 Node，封存原文及身份链，观察当前能力和目标所需状态；动作脑收到有版本的任务包。
2. 动作脑可以规划多个有序步骤，但 Node 每次只派发前置条件有效且取得执行权的步骤。预先验证的后续确定性步骤可直接继续，需要新决策时才续轮，不为每个动作 tick 调模型。
3. 长步骤快速返回 `accepted + taskId`，随后由任务事件给出终态与证据。外部项目的“工具必须 11 秒内结束”等限制不照抄为游戏任务时限；宿主工具超时与游戏任务存续分别管理。
4. Node 按 request/plan/step/task/attempt 和计划版本关联事件，持久化后去重投递。动作脑需要知道阶段完成、失败、条件改变、停滞、玩家指导时再收到续轮；无新事件等待，不让 LLM 定时轮询任务是否结束。传输层保活或程序查状态不等于模型调用。
5. Node 独立检查库存、设备、世界或 GUI 后置条件，再结算。`accepted`、harness `final` 文本、程序退出 0 和矿块消失都不能单独证明任务成功；采矿必须保持挖块及对应产物入包契约。
6. 急停/反射/死亡/断线先在 Node 撤销旧版本执行资格并停止身体，再尝试取消模型回合。即使宿主无法立刻结束模型请求，迟到输出也不能恢复操作；在途请求可能仍计费，需入账。
7. 进程重启后先从 Node 恢复进度和未答问题，再重新观察、确认恢复条件；不自动重放已执行动作。harness 会话丢失时可按任务包重建上下文，无法确认的动作保持 unknown。

**会话生命周期与状态归属（Q8）**：一个服务器一个长会话、一个任务一个 turn；Node 持有权威计划与身份链，harness 只持对话上下文；会话空闲 30 分钟关闭（可配），重建时只注入"任务包 + 未完成步骤 + 未答问题"，不注入历史对话全文。两个接入模型均为 **deepseek-flash（DeepSeek V4.1 Flash）**。

上下文保留原始目标、约束、最近观察、能力摘要、未完成步骤、关键结果、待答问题与相关方法；工具全文和旧日志按需取用。框架自己的摘要必须能与 Node 事实对账，不能覆盖原始任务。`SKILL.md` 可作为提示与流程资料，不能替代本项目带 manifest、可取消且经过效果验证的可执行技能。

#### 1.9.4 工作量与维护归属

两条路线**共同必须做**：§1.4 的身份/能力/进度/结果重构、唯一执行权、停止和迟到失效、持久化计划/问题、§1.7 候选隔离和晋升、§1.8 CU 反馈。不能把这些全部记在 harness 接入账上，也不能把自研直接调用旧接口当作已经解决。

仓库复用点与缺口：

- [`src/llm/client.js`](../src/llm/client.js) 已有模型请求、超时/取消及基础 usage 统计；还需逐请求记账、失败/流中断记录、缓存/推理计费口径与供应商账单核对。
- [`src/llm/index.js`](../src/llm/index.js) 和 [`tools/registry.js`](../src/llm/tools/registry.js) 已有有限工具回合。完成事件按首个未关闭请求匹配、后续偏播报的流程需改为身份关联的可恢复闭环，不能直接当作完整规划器。
- [`TaskHub`](../src/core/taskHub.js) 已有单任务、替换和停止机制；父计划/子步骤适配必须避免重复 submit 把父任务替换。
- [`miningRecovery.js`](../src/skills/miningRecovery.js) 的观察、模型、校验、单步执行、验证循环可提供经验，但只解决局部采矿异常，不承担通用任务规划。

| 路线 | 新增主要工作 | 后续维护重点 |
| --- | --- | --- |
| harness | 工具桥、宿主事件续轮、会话/取消适配、任务包与上下文、预算/usage 接入、固定配置 | 上游版本升级、事件语义、模型协议、内置工具边界和费用可见性回归 |
| 自研 | 多轮循环、工具参数与错误处理、预算/重试、上下文压缩、恢复、文件编辑/运行/修复工具链 | 模型协议变化、循环质量、失败模式、上下文与编码工作流持续演进 |

先完成小实验再估算生产接入剩余工作，不给未经测量的“接入几小时即可完成 P1”承诺。独立实验将人时与 API 成本分账，测一次接口变更的维护成本；其预算只是实验范围，不能用作完整 P1 工期报价。

#### 1.9.5 接入验收与选型决策

- 沿用 A04–A08 验证事件关联、执行权、真实结果与停止；A13–A20 验证完整规划、学习、代码生成和晋升，不因接入第三方而降低要求。
- 新增 A27–A31 验证模型/工具兼容、宿主续轮、状态恢复、用量/预算口径与事件汇聚重放。自研后端也必须满足等价契约，harness 专属会话测试记录为后端适用项。
- 独立实验只回答“当前版本、模型和小范围任务下，哪条路线值得继续”，不作为 P1 全部能力已通过的证据。通过结果需记录后端版本、公开/内部接口依赖、未覆盖项和选择理由。
- 默认优先接入 harness；**只有 §1.9.2 的四条降级判定成立**才进入 A/B 比较（从 §10 第 2 项 8 次配对开始）。判定与证据记入 M0，不按主观印象写胜者。

#### 1.9.6 用量政策：监控而非代码级限制（Q2）

**不对 LLM 的 token 消耗做代码级限制**：不新增 per-request / per-turn 预算闸门，动作脑的请求不因预算被拦。这是知道代价的选择，必须同时满足三条：

1. **可观测**：每次 turn 记录请求数、输入/输出 token（能取到就记，取不到记 `unknown` 并给上界），面板显示累计用量。
2. **可归属**：用量按 `requestId/planId/turnId` 落到账本，跨进程（harness 内部请求）也要尽力归属，缺失单独列出。
3. **停机后评估**：停止后核对"是否超支、超在哪、怎么优化 token 用量"，把结论写回运行记录；不做"超支即回滚"的自动裁决。

既有 `dailyTokenBudget`（`src/llm/index.js:111-114`）保留为**遗留口径**，不扩展到动作脑，也不作为 P1 的新验收项；如需与"不限制"完全一致，可在后续改为默认不拦截（本方案不预设）。

**代价（写入 §四 风险表）**：没有硬上限时，跑飞只能靠人工停止与事后评估兜底，不能承诺"绝不超支"。

### 1.10 自主规划器退役（Q4）

`slowLoop` 的规则规划器退役，拆成三件可独立验收的东西：**GoalEvaluator**（规则表 → 声明式候选，纯函数可注入）、**proposals**（提案生命周期与授权）、**TaskSlot**（唯一执行器：合并 `brain.queue/activeTask` 与 `TaskHub.current`，承接 B1/B2、holds、超时与统一事件出口）。详见 [`PLANNER-RETIREMENT.md`](PLANNER-RETIREMENT.md)。

- 开关 `planner.mode = legacy | proposals | off`，**默认 legacy**，按阶段验收后切换。
- **实施进展（2026-10-17）**：S0–S4 已全部离线交付；`pickRule()` 已删除，`decide()/buildTask()` 保留为
  legacy 后端、`slowLoop` 保留为按模式分派的调度器；`plan:audit` 已支持 `--stage p0|p1`。
  默认模式切到 `proposals` 与删除 legacy 后端**待 M6 语言脑接管提案问答后进行**。

## 二、语言聊天与自主提案

### 2.1 持久化与上下文

对话按消息 ID、发言者、来源、时间与任务关联持久化。重启恢复近期对话、重要事实、未答问题与摘要，不默认恢复身体动作。摘要保留关键约束和玩家纠正，可回查原文；当前任务指令不因摘要被替换。

语言脑根据事实事件生成开始、进展、求助和结束播报，相同事件只报一次。长任务按阶段和实质变化反馈，不按低层动作刷屏。不能提前宣称成功，也不能把 partial/unknown/cancelled 润色成全部完成。

### 2.2 状态触发的主动发言

昼夜、天气、新地貌或任务体验可成为输入。代码只负责去重、聚合和预算调度，语言模型结合近期聊天、上次发言与当前任务决定说话或沉默，并生成内容。

不采用“每次定时感知都请求 LLM 尝试发言”。无变化采样不触发语言调用，同一事件不在每次采集时重复触发。直接回应玩家、求助播报与闲聊分别调度，不能被闲聊冷却压住。

### 2.3 普通聊天插话

**语义时机交给模型判断。**普通玩家聊天无需提到 agent 名字，不应被关键词规则挡在模型之外。代码仅负责自身回声/重复消息过滤、聚合、并发、预算与发送时效，不判断对话是否“值得参与”。

1. 新普通聊天短时聚合；可先以 1 秒为可调初值，并设最长等待，持续聊天不能无限推迟判断。直接呼叫、任务回答、急停走对应入口。
2. 给语言脑近期上下文、对象、agent 最近发言、当前任务与消息序号，模型输出 `speak(text)` 或 `silence`，沉默是正常结果。
3. 沉默后等新消息或有意义事件，不因没说话而定时重试；同批不重复判断。
4. 返回后检查聊天版本；语境已更新时重新判断或丢弃过时回复，不能照发。
5. 预算不足可延迟/聚合普通闲聊，记录原因；不能把“没安排推理”记作“模型选择沉默”，不能因此漏掉显式命令与任务回答。

人工样本同时包含应插话与应沉默场景，如别人密集交谈、信息不足、话题已结束、agent 刚说过相同内容等，不能只有积极接话示范。

### 2.4 自主任务申请

空闲且没有阻塞中的显式任务时，动作脑根据已知状态提出任务建议，语言脑表达。**提案不等于获准执行。**玩家接受具体建议后绑定目标执行；另派任务则按新请求处理。

拒绝后该轮结束，至少等待原方案约定的 3 分钟，不原样反复推同一提案；无回答不视为同意。普通采样不重复触发提案；保命反射无需等待提案获准。

> **实施进展（2026-10-17，RETIREMENT S3）**：提案状态机已落地为 `src/planner/proposals.js` + `planner.mode=proposals`（默认仍 `legacy`），并用确定性入口 `!proposal status|accept [always]|reject` 做离线验收（接受 / 拒绝冷却 / 无答过期 / 另派取代 / 常驻授权）。**语言脑的措辞与回答解析仍在 M3/M6**，届时替换该入口而不改变状态机；真机多人 A25 未执行。

## 三、验收标准

### 3.1 证据要求与总体判定

分契约/回放、模型行为、真实客户端三层：确定性边界用注入模型、乱序事件与错误回执验证；人格、插话和规划用固定语料与模型运行验证；物理、GUI、网络和反射时延必须真机测量。

每次记录提交、配置/模型标识、游戏/模组版本、初态、请求/任务 ID、证据、调用数/token/耗时与失败原因。不得把待测、代码存在或模型自述算通过。**当前本节所有项目均待验收。**

契约类要求全部通过；自然语言阈值是初始建议，须冻结评测集再执行，不能事后删失败样本。场景覆盖不同目标与前置条件，不能只重复同一成功轨迹。同一验收 ID 涉及多个后端或后续功能时，分场景记录；早期阶段只通过适用子集，不得提前把整项标为全部通过。

### 3.2 分项验收清单

| ID | 项目 | 操作与输入 | 通过标准 |
| --- | --- | --- | --- |
| A01 | `!` 免语言审查 | 游戏/面板发送有效命令、非法参数、`!shoot player`；模型离线 | 准入模型调用为 0，原文完整进入解析；不因人格拒绝，执行问题明确返回 |
| A02 | 二值闸门与原文 | 至少 20 条 `@` 指令/回答；注入改写字段、错误 Schema、超时 | 只放行/拒绝；放行原文完全一致；改写字段不派发，错误有记录，不生成替代任务 |
| A03 | 职责与 persona | 检查语言工具清单和新旧规则冲突样本 | **语言脑无 body/技能/任务工具**，只保留状态摘要读取、检索/搜索、`say`/`silence`；`systemPrompt` 工具段与 registry 拆分可验证；允许合适插话/提案；不因旧能力描述误拒绝；射击事实不自动转自主偏好 |
| A04 | 事件关联 | 两请求交错、重复/乱序完成、取消后回调、迟到模型输出 | 仅推进所属请求；终态最多一次播报；不唤醒无关的首个未关闭请求 |
| A05 | 统一能力 | 同一合成等能力从命令、自然语言、规划进入，设置支持/缺料/不支持 | 共用能力来源，正确区分缺料与不支持；不因旧 supportsCrafting 单字段漏掉菜单合成 |
| A06 | 进度与完成 | 每次新对象但值不变；动作成功但库存未增、部分入包 | 检测值停滞；不把函数返回/矿块消失算全部成功；保留 partial/pending；不无限重选同一失败目标 |
| A07 | 身体互斥 | 复杂计划多个步骤，插入反射、替换、停止超时 | 只有一个执行者；子步骤不替换父计划；未停则不启第二执行者；恢复前校验 |
| A08 | 停止与迟到输出 | 模型等待、搜索、技能动作、GUI 长按时分别急停/死亡/断线/接管 | 本地停止满足既有 3 秒要求，不等模型返回；按键释放，旧输出失效；死亡/重启不自动续动作；无停止确认则保持阻塞 |

| CU 窗口限制依赖插件能力 | 无法限窗则超范围操作 | M0 的 F1 闸门验证；做不到即放弃 CU（§1.8.3），M5 相应验收标 N/A |
| 插话无完全客观答案 | 抢话、迟到或过度沉默 | 固定正反例、过时处理、真机人工复核；A23、A24，不承诺零误判 |
| 日志增长/摘要丢条件 | 上下文成本和旧知识污染 | 分类、预算、回溯与条件检查；A16、A17 |
| 玩家不答或条件确实受限 | 无法保证完成 | 保存等待/阻塞，避免催问，接受指导/取消/替代路径；A14、A15、A25 |
| 掉落物被他人拾取/销毁 | 挖掉不等于本玩家收获 | 沿用入包证据和台账，部分/未知如实报，不保证必然捡到 |
| P0 审计与 P1 范围冲突 | 误挡新功能或误删有效约束 | M0 登记、逐阶段迁移；A26，历史记录不改成 P1 结果 |
| harness 版本/宿主接口变化 | 续轮、取消或工具协议失效 | 固定版本、列公开/内部依赖，升级重放；A27–A29。首选接口不可用时评估轻量自研，不无限补内部补丁 |
| 双重规划或误把会话当任务数据库 | 重复执行、丢已完成步骤、重启错误续动作 | 一个高层规划者，Node 保存事实、仲裁和验证；A04–A08、A28、A29 |
| 框架内部请求/订阅费用不透明 | 表面调用少但总成本漏计 | 动作脑用量监控、按 turn 归属、缺 usage 记 unknown 与上界；停机后复盘（§1.9.6） |
| **无代码级 token 上限** | 跑飞时超支只能人工停止 | 面板显示累计用量；停机后评估超支与优化项；**不承诺"绝不超支"** |
| 自研通用设施持续膨胀 | 从轻量循环逐步演变成需维护的专用 harness | 分开记录共用/专属人时；保留适配接口，按真实扩展和维护成本复评 |
| 小样本/Mock 结果外推 | 把规划成功误认为真机和长期自主能力成熟 | 独立实验限定结论范围，真实物理、GUI、长期学习仍走 P1 正式验收 |

单服务器、按需感知、有限预算和确定性执行是当前工程取舍。P1 不保证任意模组、GUI、自然语言目标都能自主完成；必须能学习、求助、保留进度并准确报告实际结果。
